## 一、先看清难点在哪（复杂度地图）

自写代码（不含 Gazebo world 与 rviz 配置）：

| 类型 | 文件 | 行数 |
| --- | --- | --- |
| Python | 36 | 1,747 |
| C++（`.cpp`） | 16 | 1,327 |
| C++（`.hpp`） | 4 | 156 |
| launch | 8 | 712 |
| xacro / urdf | 16 | 865 |
| yaml 配置 | 4 | 499 |
| **合计** | | **≈ 5,300** |

分布极不均匀：

| 包 | 行数 | 性质 |
| --- | ---: | --- |
| `robot/mybot_description` | **≈ 1,990** | 模型 + 世界 + **299 行的仿真编排** |
| `navigation/mybot_navigation2` | 559 | 含 **429 行的 `nav2_params.yaml`** |
| `robot/gz_sensor_bridge` | 445 | 最大的单个 C++ 文件 |
| `navigation/nav2_custom_planner` + `nav2_custom_controller` | 399 | 自写插件 |
| `robot/mybot_bringup` | 393 | 启动编排 |
| `app/autopatrol_robot` | 363 | 最完整的应用 |
| **12 个 `learning/*` 包** | **931** | **与主线零耦合，可整体后置** |

### 结论

1. **代码量不构成门槛** —— 主线 ≈ 4,400 行，其中需要**逐行读懂**的核心只有约 **2,000 行**
   （两个插件 399 + 桥接节点 445 + 应用 363 + 各 launch 的关键段）。
2. **真正的难点是「参数与集成的因果链」** —— `nav2_params.yaml` 一个文件就 429 行，
   而 `docs/问题记录.md` 里那些坑，绝大多数属于这一类，不是算法问题。
3. **12 个学习型包（18% 的代码）可以完全跳过**，它们不影响对机器人的任何理解。

> 由此决定：掌握路线应该围绕**层与验收**来组织，而不是「读完所有代码」。

## 二、五层掌握模型

每一层都给一个**可判定的验收动作**。没通过就别往下一层走。

### L1 · 能跑 ｜ 验收：从零起来并看到机器人动

```bash
./scripts/start.sh                     # 起容器
./scripts/sim.sh --headless            # 另开一个终端
./scripts/shell.sh -c 'bash /workspace/my-slam/tools/check_topic_health.sh'
./scripts/teleop.sh                    # 让它动起来
./scripts/stop-all.sh                  # 收工
```

**通过标准**：`check_topic_health.sh` 退出码 0，7 个话题**发布者都是 1**、频率达标。

**这一层不需要读任何代码** —— `scripts/` 下 18 个脚本已经封装好了。

### L2 · 知道有什么 ｜ 验收：能画出 TF 树和话题图

```bash
./scripts/shell.sh -c 'ros2 run tf2_tools view_frames'   # 生成 frames.pdf
./scripts/rqt.sh                                         # Plugins → Node Graph
python3 tools/show_graph.py
```

**通过标准**：能回答「`map → odom → base_footprint` 各自**由谁发布**」——
见本文第六节《关键点速查》的 Q1（带证据）。

> **没写过 ROS 2 的话，先做一遍
> [`模块详解-mybot_description.md`](模块详解-mybot_description.md) 的「第零节：零基础七步」。**
> 那七步就是 L2 的具体做法（每一步：敲什么 → 看到什么 → 说明什么，都是实测输出），
> 做完你就有了本节要求的 TF 与话题认知。

这是全项目**最重要的一个认知**。绝大多数「导航不动」的问题，最后都追到 TF 上。

### L3 · 知道连成什么样 ｜ 验收：能讲清一次导航指令的完整旅程

要读的文件不多，总共约 1,200 行，但这是整个项目的骨架 —— 见下一节。

**通过标准**：不看图能讲出

```text
rviz 目标点 → bt_navigator → planner_server → controller_server
   → /cmd_vel_nav → velocity_smoother → /cmd_vel_smoothed
   → collision_monitor → /cmd_vel → mybot_diff_drive_controller → 差速运动
```

并说出**每一级为什么必须存在**（README「Nav2 的速度链」一节已画好，但你要能自己复现它）。

### L4 · 能改对 ｜ 验收：做 3 个改动，每个都「先预测、再测量、后对比」

难度递增：

1. **雷达频率 5 → 15 Hz** → 用 `tools/check_topic_health.sh` 验证，并观察 CPU 占用变化
2. **改巡航速度 / 膨胀半径** → 用 `tools/map_reachability.py` 确认新路径仍可达
   （**别只看「导航成功了没有」** —— 成功可能是靠 planner 绕远路换来的）
3. **给 `nav2_custom_planner` 加一个新行为**（例如「尽量贴墙走」）→
   用 `tools/make_custom_plugin_params.py` 生成测试参数

**通过标准**：每次改动都**先说预期、再测、再对比**。如果改完只能说「好像更好了」，
说明还在 L3。

> 这一层的关键纪律：**改动必须能被证伪**。写不出「如果我说错了，会观察到什么」，
> 就还不算会改。

### L5 · 能定位坏在哪 ｜ 验收：自己走完一次完整排查

```bash
bash tools/run-stuck-repro.sh        # 一键复现「卡住 → 恢复耗尽 → ABORT」
```

**通过标准**：能自己走完 `docs/问题记录.md` E-1 那条排除链，并且**知道哪些排除是有效的、
哪些不能得出结论**（区别见 E-1 与 F-9）。

## 六、关键点速查

以下 8 个问题，**每一条都有仓库内的证据**，不是泛泛而谈。

### Q1 TF 树里每一段是谁发布的？

```text
map ──(AMCL)──> odom ──(mybot_diff_drive_controller)──> base_footprint
                                                              │
                                        (robot_state_publisher)│ + /joint_states
                                                              ▼
                                                          base_link
                                                    ├─> laser_cylinder_link → laser_link
                                                    ├─> camera_link → camera_optical_link
                                                    ├─> imu_link
                                                    └─> left_wheel_link / right_wheel_link
```

| 段 | 发布者 | 证据 |
| --- | --- | --- |
| `map → odom` | **AMCL** | `nav2_params.yaml`：`amcl.tf_broadcast: true`、`global_frame_id: map`、`odom_frame_id: odom` |
| `odom → base_footprint` | **`mybot_diff_drive_controller`** | `mybot_ros2_controller.yaml`：`odom_frame_id: odom`、`base_frame_id: base_footprint`、`enable_odom_tf: true` |
| `base_footprint → base_link → 各传感器/轮子` | **`robot_state_publisher`**（由 `/joint_states` 驱动） | `gazebo_sim_gz.launch.py` 起 `robot_state_publisher`；`/joint_states` 由 `mybot_joint_state_broadcaster` 发 |

**记忆点**：三个发布者对应三种**不同的坐标系语义** —— 全局估计 / 里程计积分 / 几何结构。
分不清这三者，就永远查不清「机器人怎么突然跳了」。

### Q2 为什么 `/cmd_vel` 链上要夹 `velocity_smoother` 和 `collision_monitor`？

**先记住一个反直觉的事实**：`/cmd_vel` 的**发布者不是 `controller_server`**，
而是 `collision_monitor`。用 `ros2 topic info /cmd_vel -v` 可以验证。
所以调试「车不动」要**从这条链的末端往回查**。

| 环节 | 存在的理由 | 拿掉会怎样 |
| --- | --- | --- |
| `velocity_smoother` | 限制加速度/角加速度，把 controller_server 输出的突变速度平滑掉 | 速度阶跃 → 实机上打滑、丢步，里程计误差被放大 |
| `collision_monitor` | 独立的速度闸门：直接看传感器决定「能不能走」，**不依赖规划层的判断** | 失去最后一道安全闸 —— 规划器判断失误时没有兜底 |

> 本项目已实测这条链**不会吃掉指令**：三级话题同录（`tools/probe_cmd_chain.py`）显示
> 非零率都是 47%、幅值范围都是 `[0, 0.26]`，完全一致。
> 所以「车不动」时**别怀疑这一链**，先去查末端和上游。

### Q3 `wheel_separation` 配错会怎样？怎么证明？

- **现象**：走直线时航向慢慢偏；走定角度转弯时转多/转少；里程计转角与实际不符。
- **为什么难查**：它表现成「走不准」，而「走不准」也像打滑、也像 AMCL 漂移。
- **怎么证明**（必须用**外部测量**，不能看日志自述）：
  - `tools/verify_wheel_separation.py` —— 用 Gazebo 真值做 A/B
  - `tools/probe_wheel_speed.py` —— 由轮速反推控制器实际生效的参数值
- **本项目的实测**：URDF 里两轮 y 坐标是 `±0.10` → 正确值 `0.20`，
  曾经写成 `0.17`（见 `docs/问题记录.md` B-7）。
- ⚠️ **配套的坑**：用 `ros2 param set` 改它**会返回成功但不生效**，必须重启控制器
  （B-8）。这就是「测量本身是否有效」的典型案例。

### Q4 `sensor_bridge` 的两个取值分别是什么？为什么不能同时跑？

| 取值 | 含义 |
| --- | --- |
| `gz_sensor_bridge`（**默认**） | 用自写节点 `gz_sensor_bridge_node` 桥接 `/imu`、`/camera/*` |
| `parameter_bridge` | 用 `ros_gz_bridge` 的内置 `parameter_bridge` 桥接同样的话题 |

**两者已验证等价**（`docs/问题记录.md` D-1 的等价表）。

**为什么不能同时跑**：两者会发布**同一组话题** → 同一话题出现多个发布者，
频率翻倍、数据交错，且现象极其难查（D-3）。切换后必跑
`tools/check_topic_health.sh` 确认**发布者数 = 1**。

### Q5 `open_loop: true` 意味着什么？

- **含义**：里程计**不看轮子的实际反馈**，直接对**指令速度**做积分。
- **后果**：卡住、打滑、被推着走 —— 里程计都认为自己在按计划走。
- **实测影响**：巡逻一圈漂移 **7 m / 38°**（README「一个值得知道的现象：里程计会漂移」）。
- **应对**：短距离可信；长距离必须靠 AMCL 提供的 `map → odom` 修正。
  这也解释了为什么 `local_costmap` 必须用 `odom` 而不是 `map` 做全局坐标系。

### Q6 报 `Failed to make progress` 时，可能原因有哪些？各自怎么证伪？

**每条只能证伪自己，不能证明别人**（这是 F-9 的核心）：

| 候选原因 | 怎么证伪 |
| --- | --- |
| 物理阻挡 | 手动下发速度看机器人动不动；激光看前方距离 |
| AMCL 定位漂移 | 同录 AMCL 位姿与 Gazebo 真值（`tools/probe-localization-vs-truth.sh`） |
| `collision_monitor` 把速度清零 | 单独看它的话题输出 |
| 速度链某一级吃掉指令 | 三级话题同录（`tools/probe_cmd_chain.py`） |
| 目标点几何不可达 | `tools/map_reachability.py` —— **必须带一个已知不可达的对照输入** |
| 仿真变慢 / `use_sim_time` 不一致 | 测 RTF（仿真时钟 / 墙上时钟）；`ros2 param get` 逐个确认 |
| 参数检查器过严 | 看 `progress_checker` 的**实际生效默认值**（不是你以为的值） |
| **CPU 争抢** | 测 `controller_server` 的**实际循环频率** vs 配置值 |

⚠️ **本项目最后剩下的是 CPU 争抢**（实测控制器循环只有 5.75 Hz，配置是 20 Hz）——
它是靠**正面测量**确定的，不是靠排除法。**排除法永远得不出正面的原因。**

**实操建议**：验证 Nav2 时不要同时开 rviz / Gazebo GUI，CPU 争抢会让这一层误报。

### Q7 容器重建会丢什么？

- **会丢**：手工 `apt`/`dpkg` 装进**容器可写层**的东西（A-3）。
  判据：`docker diff <容器>` 里显示为 `A` 的条目。
- **不会丢**：`/workspace` 是 bind mount（源码、`install/`、世界文件都在宿主机上）。
- **本项目的现状**：`tf_transformations`、`example_interfaces` 已经写进 `Dockerfile`，
  镜像里就有 → 重建不会丢（G-3）。
- **判定「是镜像问题还是容器问题」的固定手法**：
  `docker inspect <容器> --format '{{.Created}}'` 对比
  `docker image inspect <镜像> --format '{{.Created}}'`；
  要查镜像里有什么，直接 `docker run --rm --entrypoint bash <镜像> -c 'ls -d ...'`，
  **不要拿运行中的容器当镜像的证据**。

### Q8 为什么新增文件必须重新 `colcon build`？

- `--symlink-install` 是**逐文件建软链**（A-4）。
- **改已有文件**：软链自动指向新内容 → 不用重编。
- **新增 / 移动文件**：没有对应的软链 → **必须重编**才会在 `install/` 里出现。
- 典型症状：新写的 launch 文件在 `install/` 里找不到。
