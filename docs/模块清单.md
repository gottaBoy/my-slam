# 模块清单

`my-slam/src/` 下的 **22 个包**，按功能分 4 组。本文件回答三个问题：
**每个包是干什么的 / 怎么跑起来 / 有没有真的验证过**。

> 想知道「每个包**里面**有什么、对外提供什么接口、和谁交互」→ [`模块解剖.md`](模块解剖.md)

约定：
- 「验证状态」只写**有实测证据**的结论。没验证过的写 ❓，不要当成通过。
- 「已知限制」写真实存在的限制，不写"以后会优化"这种空话。

## 分组总览

```
src/
├── robot/         机器人本体：描述、仿真、启动、传感器桥
├── navigation/    Nav2 配置与自研插件
├── app/           应用层：导航示例、巡检应用与它的接口
└── learning/      学习型示例程序（与机器人主线无耦合）
```

> 分组**只影响目录，不影响包名**：colcon 递归发现 `src/` 下的包，
> `ros2 launch` / `ros2 run` / `get_package_share_directory` 全部按包名解析，
> 所以挪目录对工具链是透明的。`tools/` 下的脚本也已改成自动搜索，
> 以后再调分组不会失效。

## robot

### `mybot_description` — 机器人描述与仿真

> 想把这个包**真正搞懂**（而不只是知道它能跑）→
> [`模块详解-mybot_description.md`](模块详解-mybot_description.md)：四个「拆开看」的动作 + 自测 5 题

- **作用**：整个仿真的主体。URDF/Xacro 模型（含 Gazebo Sim 插件）、Gazebo 世界、
  差速控制器参数、仿真启动文件、键盘遥控脚本。
- **关键内容**：
  - `urdf/mybot/` — 模型；`plugins/gz_sensor_plugin.xacro` 定义雷达/IMU/相机的
    `update_rate`（雷达 10 Hz、IMU 100 Hz、相机 10 Hz）
  - `world/custom_room_gz.world` — 房间场景
  - `config/mybot_ros2_controller.yaml` — 轮距 0.20、`open_loop: true`
  - `launch/gazebo_sim_gz.launch.py` — **主启动文件**（Gazebo Sim 版）
- **怎么跑**：

  ```bash
  ./scripts/sim.sh                        # 带 GUI
  ./scripts/sim.sh --clean --headless     # 无头（远程/CI）
  ./scripts/sim.sh -- sensor_bridge:=parameter_bridge    # 换用内置桥
  ```
- **依赖**：`ros_gz_sim`、`ros_gz_bridge`、`gz_ros2_control`、`controller_manager`
- **验证状态**：✅ 本轮反复启动；`tools/check_topic_health.sh` 退出码 0
  （6 个话题发布者均为 1，`/scan` 9.7~10.0 Hz、`/imu` 100 Hz、`/camera/camera_info` 10 Hz）；
  启动日志里 ROS→GZ 桥 **0 条**（无自激回环）
- **已知限制**：`launch/gazebo_sim.launch.py` 是 Gazebo classic 版，Jazzy 下
  **跑不起来**（`gazebo_ros` 已 EOL），保留仅作对照。
- **已知现象（非缺陷）**：ROS `/clock` 的**发布者是 2**（两个都叫 `ros_gz_bridge`）。
  原因是 gz 同时在 `/clock` 与 `/world/<world>/clock` 两个话题名下发时钟，而
  launch 里为兼容两种 gz 版本把**两条都桥了**。功能正常，但
  **「发布者必须为 1」这条判据不适用于 `/clock`**。
  `tools/check_topic_health.sh` 检查的 7 个话题里**不含 `/clock`**，所以不影响
  上面的验证结论。详情见 [`模块详解-mybot_description.md`](模块详解-mybot_description.md) 第七节。

### `mybot_bringup` — 启动

- **作用**：把"起机器人"这件事收成一条命令。真机版 + 仿真版。
- **关键内容**：
  - `launch/bringup_sim.launch.py` — 仿真版一键启动（Gazebo + Nav2 + 可选设初始位姿）
  - `launch/bringup.launch.py` — **真机版**
  - `src/odom2tf.cpp` — 把 `/odom` 转成 TF（**仅真机需要**）
- **怎么跑**：

  ```bash
  ros2 launch mybot_bringup bringup_sim.launch.py          # 默认带 GUI
  ros2 launch mybot_bringup bringup_sim.launch.py headless:=true rviz:=false
  ```
  可配参数：`headless`、`rviz`、`initial_pose`、`pose_delay`
- **验证状态**：✅ `bringup_sim.launch.py` 实测启动 0 错误，两个 lifecycle manager 均 active
- **已知限制**：`bringup.launch.py` 依赖 `ydlidar`、`micro_ros_agent`、
  `ros_serial2wifi` 三个**未安装**的包，直接跑会得到
  `PackageNotFoundError: "package 'ydlidar' not found"`。
  **按原样保留，不在本地跑**（真机场景用）。
  另外仿真版**刻意不含 `odom2tf`** —— 仿真里 `odom→base_footprint` 已由
  差速控制器发布，再加一个会出现两个发布者互相打架。

### `gz_sensor_bridge` — 传感器桥（可选）

- **作用**：把 gz 的 `/imu` 与 4 个 `/camera/*` 话题转成 ROS 话题。
- **怎么跑**：由 `gazebo_sim_gz.launch.py` 默认拉起，一般不用单独跑。
- **验证状态**：✅ 与内置 `parameter_bridge` 实测**等价**：6 个话题发布者均为 1、
  `/imu` 99.4 vs 99.6 Hz、`/camera/camera_info` 9.94 vs 9.99 Hz、
  `/imu` 的 `frame_id` 都是 `imu_link`、数据自洽自检退出码 0、ROS→GZ 桥 0 条
- **已知限制**：**它不是必需的**。早先曾把 `parameter_bridge` 桥不出这几个话题
  归因于上游缺陷，该结论**已撤回**（原因未定位、当前无法复现）。
  现在两套实现由 launch 参数 `sensor_bridge` 切换，**两者不能同时开**。

## navigation

### `mybot_navigation2` — Nav2 配置与地图

- **作用**：Nav2 全套参数、预制地图、rviz 配置、导航启动文件。
- **关键内容**：`config/nav2_params.yaml`（本项目 8 处 Jazzy 适配都在这里）、
  `maps/room.pgm` + `room.yaml`（376×222 px @ 0.05 m，origin `-10.4,-6.53`）、
  `rviz/mybot_nav2.rviz`、`launch/navigation2.launch.py`
- **怎么跑**：`ros2 launch mybot_navigation2 navigation2.launch.py rviz:=false`
  （或直接用 `bringup_sim.launch.py`，它会按延迟拉起 Nav2）
- **验证状态**：✅ 导航与巡逻实测；到位误差 0.16~0.38 m
- **已知限制**：
  - 默认**仍用官方 `DWBLocalPlanner` / `NavfnPlanner`**，自研插件写在注释里作备选
  - 地图是 SLAM 建出来的，与 world 几何**不完全一致**（分区判断见 `docs/问题记录.md`）
  - 目标点是否可达请先用 `tools/map_reachability.py` 确认

### `nav2_custom_planner` / `nav2_custom_controller` — 自研插件

- **作用**：Nav2 全局规划器 / 控制器插件示例。
- **怎么跑**：默认不启用。想体验时生成临时参数文件覆盖：

  ```bash
  python3 tools/make_custom_plugin_params.py /tmp/nav2_custom_test.yaml
  # 然后 launch 时传 params_file:=/tmp/nav2_custom_test.yaml
  ```
- **验证状态**：✅ 插件加载成功（`Created global planner plugin GridBased of type
  nav2_custom_planner::CustomPlanner` 等）、生命周期全 active、到位误差 **0.077 m**
- **已知限制**：规划器是**起终点直线插值、不绕障**；控制器只是朝目标直行、限速
  0.1 m/s。设成默认会让已验证的巡逻/导航直接降级，所以**刻意不启用**。

## app

- **作用 / 可执行**：`init_robot_pose`、`nav_to_pose`、`waypoint_follower`、`get_robot_pose`
- **怎么跑**：

  ```bash
  ./scripts/shell.sh -c 'ros2 run mybot_application nav_to_pose'
  ```
  （需要先起仿真 + Nav2）
- **验证状态**：✅ 4 个节点逐个实测：`nav_to_pose` 到 map(1,1) 真值终点 (1.24,1.30)
  SUCCEEDED；`waypoint_follower` 走完 (0,0)→(2,0)→(2,2)

### `mybot_application_cpp` — C++ 导航示例

- **作用 / 可执行**：`nav2pose` —— 向 Nav2 发 `NavigateToPose` 目标
- **验证状态**：✅ 到 map(2,2) 真值终点 (2.22,1.90)
- **已知限制**：曾漏填 `orientation`（四元数全 0，非法姿态），已补 `w=1.0`；
  该改动**不改变可观测结果**，只是消除非法值。

### `autopatrol_interfaces` — 巡检接口

- **作用**：定义巡检应用的自定义服务。
- **关键内容**：`srv/SpeachText.srv`：
  ```

  ---
  bool result    # 合成结果
  ```
- **验证状态**：✅ 编译通过，被 `autopatrol_robot` 正常调用

### `autopatrol_robot` — 巡检应用

- **作用 / 可执行**：`patrol_node`（巡逻主循环）、`speaker`（语音播报服务端）
- **怎么跑**：`ros2 launch autopatrol_robot autopatrol.launch.py`
- **验证状态**：✅ 5/5 巡逻点全部到达
- **已知限制**：语音**只打日志不发声** —— 本机没有 `espeak-ng`、也没有音频设备。
  节点做了优雅降级（`try: import espeakng`），服务名/类型/返回值保持不变，
  所以调用方无感。

## learning

12 个学习型包，都是独立演示程序，**与机器人主线没有耦合**，可以单独跑。

| 包 | 可执行 | 演示什么 |
| --- | --- | --- |
| `learn_compose` | `intra_process_pubsub` | 同进程零拷贝通信（**与 docker compose 无关**） |
| `learn_dds_cpp` | `shm_pub` | DDS 共享内存通信 |
| `learn_executor_cpp` / `_py` | `learn_executor` | 执行器：单线程 / 多线程 / 回调组 |
| `learn_lifecyclenode_cpp` / `_py` | `learn_lifecyclenode` | 生命周期节点状态切换与回调 |
| `learn_message_filter_cpp` / `_py` | `timesync_test` | message_filters 消息时间同步 |
| `learn_qos_cpp` / `_py` | `reliability_test` | QoS 可靠性 / 历史深度的影响 |
| `my_tf_cpp` / `my_tf_pkg` | `static_tf_broadcaster`、`dynamic_tf_broadcaster`、`tf_listener` | TF2 静态/动态变换广播与监听 |

- **怎么跑**（以 TF 为例）：

  ```bash
  ./scripts/shell.sh -c 'ros2 run my_tf_pkg static_tf_broadcaster'   # 终端 1
  ./scripts/shell.sh -c 'ros2 run my_tf_pkg dynamic_tf_broadcaster'  # 终端 2
  ./scripts/shell.sh -c 'ros2 run my_tf_pkg tf_listener'             # 终端 3
  ```
- **验证状态**：✅ 全部跑过。`my_tf_*` 的数值还做了手算核对：

  | 包 | 广播的变换 | listener 查的 | 实测输出 | 手算 |
  | --- | --- | --- | --- | --- |
  | `my_tf_pkg` | `base_link→camera_link` (0.5,0.3,0.6) roll 180°<br>`camera_link→bottle_link` (0.2,0,0.5) | `base_link→bottle_link` | 平移 (0.7, 0.3, 0.1)<br>欧拉角 (π, 0, 0) | 一致 ✅ |
  | `my_tf_cpp` | `map→target_point` (5,3,0) yaw 60°<br>`map→base_link` (2,3,0) yaw 30° | `base_link→target_point` | 平移 (2.598, −1.5, 0)<br>yaw 0.5236 rad | 一致 ✅ |

  （`my_tf_pkg` 的三帧链是 `base_link→camera_link→bottle_link`，所以 listener 必须先起
  两个 broadcaster；`my_tf_cpp` 的 listener 带 1 秒容差、每 5 秒打印一次。）

## 怎么一次性验证全部

```bash
# 1. 编译（22 个包，应当 0 失败）
./scripts/shell.sh -c 'cd /workspace/my-slam && colcon build --symlink-install'

# 2. 起仿真
./scripts/sim.sh --clean --headless

# 3. 传感器健康（发布者数必须为 1、频率达标）
./scripts/shell.sh -c 'bash /workspace/my-slam/tools/check_topic_health.sh'

# 4. 传感器数据自洽性
./scripts/shell.sh -c 'python3 /workspace/my-slam/tools/check_sensor_msgs.py; echo exit=$?'

# 5. 停
./scripts/stop-sim.sh
```

Nav2 / 巡逻 / 应用层的回归步骤见 README 的「回归清单」。

## 新增包时放哪一组

| 新包的性质 | 放哪 |
| --- | --- |
| 机器人模型、仿真世界、启动、传感器桥 | `robot/` |
| Nav2 配置、规划器/控制器插件、地图 | `navigation/` |
| 业务应用与它的接口定义（`*_interfaces`） | `app/` |
| 教学/演示性质、与机器人主线无耦合 | `learning/` |

放好后 `colcon build` 即可 —— **不需要**改任何 launch / 脚本（都按包名解析）。
只有**新增常驻节点**时要记得把进程名加进 `sim.sh` 的清理列表，否则 `--clean` 清不掉，
会出现同一话题多个发布者（`docs/问题记录.md` 的 D-3）。
