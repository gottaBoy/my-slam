## A. 构建与环境

### A-1 容器里装不了系统包

- **问题**：想在容器里 `apt install`，一直失败。
- **现象**：`apt` 报权限错误；容器默认登录用户是 `nvidia`，不是 root。
- **原因**：`compose.yaml` 里以非 root 用户运行（这是有意的，避免产物属主变成 root）。
- **解决**：走 docker 显式指定用户，不用 `sudo`：

  ```bash
  docker compose -f my-slam/compose.yaml exec -T -u root slam-ros2-dev \
    bash -lc 'apt-get update && apt-get install -y <pkg>'
  ```

  **代价**：`-u root` 装出来的文件属主可能是 root，装完注意别让构建产物被 root 污染。

### A-2 `packages.ros.org` 慢到不可用

- **问题**：`apt-get update` 拉 ROS 索引要两分多钟。
- **现象**：实测 `packages.ros.org` 约 **14 KB/s**（2.0 MB 索引 ≈ 140 s）；
  换成 `mirrors.ustc.edu.cn` 约 **5.8 MB/s**，快约 400 倍。Ubuntu ports 官方源同样慢。
- **原因**：境外源在本机网络环境下带宽受限。
- **解决**：`Dockerfile` 新增的依赖层默认走国内镜像（`APT_USE_CN_MIRROR=1`），
  需要时可用 `--build-arg APT_USE_CN_MIRROR=0` 切回官方源。
  **注意**：镜像里 apt 源是"永久改写"的（用 `while` 循环写的，不是 `trap`），
  重建后容器内的源会一直指向 USTC/TUNA。

### A-3 依赖只装在运行中的容器里，重建就没了

- **问题**：`ros-jazzy-tf-transformations`、`ros-jazzy-example-interfaces` 装好了能跑，
  但换台机器 / 重建容器就报找不到。
- **现象**：编译时报 `Could not find ... example_interfaces`。
- **原因**：依赖只装进了**当时正在运行的那个容器实例**，没有写进 `Dockerfile`
  （镜像构建时间早于 `Dockerfile` 改动时间）。
- **解决**：把两个依赖补进 `Dockerfile` 的依赖层，**重建镜像**，并进容器验证已固化。

### A-4 `--symlink-install` 下新增文件也必须重新编译

- **问题**：改了代码却"没生效"，或者"明明文件在源码里，install 里却没有"。
- **现象**：新写的 `bringup_sim.launch.py` 在 `install/` 里找不到。
- **原因**：`colcon build --symlink-install` 是**逐文件建软链**。改已有文件不用重编
  （软链自动指向新内容），但**新增文件没有对应的软链**，必须重编才会生成。
- **解决**：新增文件后一定重新 `colcon build --symlink-install`。

### A-5 宿主机没有 numpy，跑不了仓库里的分析脚本

- **问题**：在宿主机上跑不了仓库里的分析脚本。
- **现象**：`python3 tools/check_map_point.py` 报
  `ModuleNotFoundError: No module named 'numpy'`。
- **原因**：脚本是给容器内用的，宿主机 Python 没装 numpy。
- **解决**：所有分析脚本都在容器里跑：

  ```bash
  docker compose -f my-slam/compose.yaml exec -T slam-ros2-dev \
    bash -lc 'cd /workspace/my-slam && python3 tools/xxx.py ...'
  ```

## B. Nav2 参数：Humble → Jazzy 迁移

> 这一批是沿用 Humble 时代写法的配置，直接拿到 Jazzy 下用必然撞到的坑。全部改动集中在
> `src/navigation/mybot_navigation2/config/nav2_params.yaml`，每条都在注释里留了原始报错。

### B-1 插件类名分隔符变了

- **问题**：`planner_server` / `controller_server` 起不来，说插件类不存在。
- **现象**：`planner_server: class ... does not exist`（控制器侧同）。
- **原因**：插件类名的写法从 `包名/类名` 改成了 `包名::类名`（C++ 作用域解析）。
- **解决**：全部写成 `nav2_navfn_planner::NavfnPlanner`、`dwb_core::DWBLocalPlanner` 这种形式。

### B-2 手写 `plugin_lib_names` 会导致重复注册并崩溃

- **问题**：bt_navigator 一启动就报重复注册，容器直接段错误。
- **现象**：

  ```text
  ID [ComputePathToPose] already registered
  ```

  随后 `component_container_isolated` 段错误。
- **原因**：配置里在 `plugin_lib_names` 下**逐个列出了全部内置 BT 节点**；Jazzy 已经自动
  注册了这些节点，再列一遍就是重复注册。
- **解决**：把 `bt_navigator.plugin_lib_names` **整段注释掉**（Jazzy 会自动注册）。
  **坑里有坑**：不能改成 `plugin_lib_names: []`（空列表）——会报
  `Expected 'value' to be one of [float, int, str, bool, bytes], but got '()' of type 'tuple'`
  导致 launch 直接失败。**只能注释掉**。

### B-3 Jazzy 会无条件启动 `collision_monitor`，缺配置就报错

- **问题**：启动 Nav2 时 `collision_monitor` 报参数未初始化。
- **现象**：`parameter 'observation_sources' is not initialized`。
- **原因**：原来的 `nav2_params.yaml` 里根本没有 `collision_monitor` 段，
  但 Jazzy 的 launch 会把它拉起来。
- **解决**：在参数文件里补一段 `collision_monitor` 配置（用雷达做 `observation_sources`）。

### B-4 Jazzy 会无条件启动 `docking_server`，缺配置报两个错

- **问题**：`docking_server` 起不来，报类型不兼容 + 没给插件。
- **现象**：

  ```text
  incompatible type ... Twist_
  Charging dock plugins not given!
  ```

- **原因**：同样是没有配置段，而 Jazzy 会启动它；且它需要
  `enable_stamped_cmd_vel` 与 `dock_plugins`。
- **解决**：补 `docking_server` 配置段，含 `enable_stamped_cmd_vel: True` 与
  `dock_plugins: ['simple_charging_dock']`。

### B-5 `Twist` → `TwistStamped`：车收到指令却不动

- **问题**：Nav2 一切正常、规划也出来了，**车就是不动**；手动发 `/cmd_vel` 能动。
- **现象**：Nav2 日志里看不到明显错误；`/cmd_vel` 上没数据或类型不匹配。
- **原因**：Jazzy 的 Nav2 节点默认发 `geometry_msgs/msg/TwistStamped`，
  而差速控制器按配置订阅带时间戳的版本；类型/开关不一致，指令就断在中间。
- **解决**：在**5 个**节点里都加 `enable_stamped_cmd_vel: True`：
  `controller_server`、`behavior_server`、`velocity_smoother`、`collision_monitor`、
  `docking_server`。
  **验证方法**：`ros2 topic info /cmd_vel --verbose` 看类型是否为 `TwistStamped`。

  > 顺带记录速度链拓扑（本项目实测，改参数前必须知道）：
  > `controller_server` / `behavior_server` → `/cmd_vel_nav` → `velocity_smoother`
  > → `/cmd_vel_smoothed` → `collision_monitor` → `/cmd_vel` → 差速控制器。
  > `docking_server` 只在对接时也直接发 `/cmd_vel`。

### B-6 参数名单复数写错

- **问题**：`progress_checker` 配置不生效。
- **现象**：按单数名去查是 `Parameter not set`，按复数名 `progress_checker_plugins`
  才能取到 `['progress_checker']`。
- **原因**：Jazzy 里是复数 `progress_checker_plugins`，原来的写法是单数。
- **解决**：改成 `progress_checker_plugins: ['progress_checker']`。

### B-7 轮距 `wheel_separation` 与 URDF 不一致

- **问题**：车走直线跑偏、原地转向角度不准，进而影响建图与定位质量。
- **现象**：`mybot_ros2_controller.yaml` 里 `wheel_separation: 0.17`，
  而 URDF 里两轮安装位置是 `y = ±0.10`（即 0.20）。
- **原因**：这个 0.17 是更早版本的数值，没有跟着 URDF 一起更新 ——
  轮距曾经按 URDF 修正过一次，但那份修正没有同步到本文件，于是又用回了旧值。
- **解决**：按 URDF 证据固定为 `wheel_separation: 0.20`，并做 A/B 实验验证：

  | 配置 | 真值终点与目标的偏差 |
  | --- | --- |
  | 0.17 | **−14.96%** |
  | 0.20 | **−0.41%** |

  复核脚本：`tools/verify_wheel_separation.py`。

### B-8 运行时 `ros2 param set` 改轮距"看起来生效了其实没有"

- **问题**：用 `ros2 param set` 把 `wheel_separation` 改成 0.20，跑完发现"改了没差别"，
  差点得出"该参数无影响"的错误结论。
- **现象**：`ros2 param set` 返回 success，但车的运动学行为完全没变。
- **原因**：`diff_drive_controller` **不会在运行时重新读取该参数**，必须重启控制器。
- **解决**：
  1. 要改轮距 → 改配置文件后**重启控制器**；
  2. 加一个独立手段确认"参数真的作用到了被测对象上"
     （`tools/probe_wheel_speed.py` 由轮速反推实际下发的参数值）。
  **教训**：先证明"测量本身有效"，再下结论。

## C. 插件与节点代码

自定义规划器 `nav2_custom_planner`、自定义控制器 `nav2_custom_controller`
两个包从能编译、能加载到能跑通，一共 **4 类**问题（C-1 ~ C-4）；
其余节点/包代码在移植时的问题见 **C-5 起**。

### C-1 `nav2_core/exceptions.hpp` 这个头文件没了

- **问题**：插件包编译不过。
- **现象**：`fatal error: nav2_core/exceptions.hpp: No such file or directory`
- **原因**：Jazzy 把这个头拆成了四个专用头。
- **解决**：按角色选用 —— 规划器用 `nav2_core/planner_exceptions.hpp`，
  控制器用 `nav2_core/controller_exceptions.hpp`（另有 `smoother_exceptions.hpp`
  / `route_exceptions.hpp`）。

### C-2 抽象类实例化失败：`createPlan` 签名变了

- **问题**：插件包编译不过。
- **现象**：`invalid new-expression of abstract class type 'CustomPlanner'`
  （提示 `createPlan` 未覆盖纯虚函数）
- **原因**：Jazzy 的 `GlobalPlanner::createPlan` 多了一个参数
  `std::function<bool()> cancel_checker`。
- **解决**：补上该参数，并在生成路径的循环里用它实现"中途可取消"。

### C-3 抛出的异常类型不对，导致异常永远不会被捕获（隐藏 bug）

- **问题**：控制器插件里抛异常后行为异常，但没有对应的错误日志。
- **现象**：日志里看不到预期异常处理路径。
- **原因**：代码抛的是 `nav2_core::PlannerException`，而 `controller_server`
  只捕 `nav2_core::ControllerException`。
  用 `strings libcontroller_server_core.so` 验证过，里面只有
  `N9nav2_core19ControllerExceptionE`。
- **解决**：控制器插件里改成抛 `nav2_core::ControllerException`。
  **这条是"编译能过、逻辑能跑，但错误处理静默失效"的典型隐藏 bug，值得单独记。**

### C-4 插件描述文件 `.xml` 缺 `name` 或用了旧分隔符

- **问题**：插件编译通过，但运行时加载不到类。
- **现象**：启动时报找不到插件类。
- **原因**：
  - `nav2_custom_controller.xml` **整段缺少 `name` 属性**；
  - `nav2_custom_planner_plugin.xml` 里写的是 `nav2_custom_planner/CustomPlanner`
    （旧分隔符）。
- **解决**：补上 / 改为 `name="nav2_custom_planner::CustomPlanner"`、
  `name="nav2_custom_controller::CustomController"`。

> **刻意选择**：插件包虽然编译、加载、跑通（到位误差 0.077 m），但
> `nav2_params.yaml` 里**默认仍用官方 `DWBLocalPlanner` / `NavfnPlanner`**，
> 自定义插件作为注释掉的备选。理由是默认路径更稳，自定义插件主要用于演示。

### C-5 发导航目标时朝向是非法四元数

- **问题**：C++ 节点发目标点后，消息里的 `orientation` 是非法姿态。
- **现象**：只填了 `position`，`orientation` 保持默认全 `0`（即 `w=0, x=y=z=0`），
  不是合法的单位四元数。
- **原因**：构造目标消息时漏填 `orientation`。
- **解决**：补上 `goal_msg.pose.pose.orientation.w = 1.0;`（显式表示"朝向不变"）。
  **注意**：这个改动对可观测结果**没有影响**（改前改后 Nav2 行为一致），
  目的是消除非法四元数、不给下游留隐患。不要把它当成"修好了某个 bug"来宣传。

### C-6 包里的节点没全部注册，`ros2 run` 找不到

- **问题**：包里 4 个节点只有一个能跑起来。
- **现象**：`ros2 run <包名> <节点名>` 对除一个之外的节点都报找不到可执行文件。
- **原因**：`setup.py` 的 `console_scripts` 里**只注册了一个入口点**。
- **解决**：把该包的 4 个节点全部注册进 `console_scripts`。

### C-7 语音播报节点的依赖不存在，一启动就崩

- **问题**：语音播报节点启动就 `ImportError`。
- **现象**：模块顶层直接 `import espeakng`，而本机没有 `espeak-ng`、也没有音频设备。
- **原因**：硬依赖一个本机不存在的包。
- **解决**：改成 `try: import espeakng`，失败时**降级为只打日志**；
  **服务名、服务类型、返回值全部保持不变**，所以调用方完全无感。
  **代价**：本机不会真的发声 —— 这是环境限制，不是遗漏。

### C-8 仿真出的相机话题名和代码里写的不一致

- **现象**：代码订阅 `/camera/image`，但仿真里发布的是 `/camera_sensor/image_raw`，

- **原因**：两侧话题名不一致。

  **只动 launch，不动节点的 `.py`**，保证节点代码与原实现一致、方便对照。

### C-9 真机启动文件在本机跑不起来（已知限制，按原样保留）

- **问题**：真机用的 bringup 启动文件在本机直接报错退出。

### D-1 部分话题桥接失败（`/imu`、`/camera/*`）

- **现象**：

  启动日志里每一条失败的桥都报同一句：

  2026-09-30 当时记录下来的观察（都在这个环境里实测过）：

  | 观察 | 结果 |

  | 同一份参数连跑 3 次 | 失败集合**完全相同**，不像“时好时坏” |

  2026-09-30 当时的结论是「上游 arm64 构建缺陷」—— **该结论已于 2026-10-01 撤回**。
  当时做过的排除（都排掉了，所以只能停在“未定位”，而不是“就是上游”）：

  | 排查项 | 做法 | 结果 |
  | --- | --- | --- |
  | 不是本仓库配置问题 | 参数、话题名、方向符、顺序都验过 | 排除 |

  key 正确）依赖按 aarch64 ABI 从 `x0/x1` 取参，而 Release 构建没有调试信息，

  **当时的处理**：改用本仓库自研的 `gz_sensor_bridge` 节点 —— 直接用 gz-transport

  ROS 消息再发布，保证下游（rviz / slam_toolbox / nav2）看到的东西和官方桥一致。
  ⚠️ 它当时的定位是「绕开上游 bug 的必要手段」，**这个理由已不成立**。

  **现在的处理：两套实现都保留，用 launch 参数二选一**（实测两者等价）：

  ```bash
  ./scripts/sim.sh --clean --headless -- sensor_bridge:=parameter_bridge   # 内置桥
  ./scripts/sim.sh --clean --headless                                     # 默认：自研桥
  ```

  两者只影响 `/imu` 与 `/camera/*`；`/scan`、`/scan/points`、`/clock` 一律交给
  `parameter_bridge`。**绝不能同时开** —— 同一话题会出现两个发布者。

  | 项目 | `parameter_bridge` | `gz_sensor_bridge`（默认） |

  | 6 个传感器话题的发布者数 | 全 = 1 | 全 = 1 |
  | `/scan` | 9.94 Hz | 9.97 Hz |
  | `/imu` | 99.43 Hz | 99.60 Hz |
  | `/camera/camera_info` | 9.94 Hz | 9.99 Hz |
  | `/imu` 的 `frame_id` | `imu_link` | `imu_link` |
  | 数据自洽自检 | 退出码 0 | 退出码 0 |
  | 启动日志里 ROS→GZ 桥 | 0 条 | 0 条 |

  保留自研桥的理由是：已验证可用、有测试覆盖，删掉没有收益。

  **若日后再现**：先跑 `bash tools/probe-bridge-types.sh` 把输出存下来 ——
  那份材料才有资格报上游。切换实现后请跑 `tools/check_topic_health.sh` 确认
  发布者数仍为 1。

### D-2 双向桥造成自激回环，`/scan` 频率飙到 18000 Hz

- **问题**：激光话题频率暴涨到完全不可用，还白烧 CPU。
- **现象**：`/scan` 从 5 Hz 飙到 **~18000 Hz**。
- **原因**：gz 的激光**本来就发布在 `/scan` 上**；如果桥再建一条 ROS→GZ 方向，
  桥会订阅自己的输出并写回 gz `/scan`，形成自激回环：
  `激光 → 桥 → ROS /scan → 桥自己订阅 → 写回 gz /scan → 桥再收 → …`。
- **解决**：`/scan`、`/scan/points` 只建**单向** `[`。
  **检查方法**：启动日志里 `grep -c "Creating ROS->GZ Bridge"` 应该是 **0**；
  `ros2 topic info /scan -v` 的 Publisher count 应该是 **1**。

### D-3 残留进程导致同一话题多个发布者，频率翻倍

- **问题**：某个话题的频率是期望值的 2~3 倍，数据重复。
- **现象**：`/imu` 曾测出 **300 Hz**（期望 100 Hz）。
- **原因**：清理脚本的进程名列表里**没包含新增的常驻节点**，
  所以 `--clean` 没把旧实例清掉；ROS 侧同一个话题于是出现多个发布者。
- **解决**：**往 launch 里新增常驻节点时，必须同步把它的进程名加进清理列表**。
  **检查方法**：`ros2 topic info /imu -v | grep "Publisher count"` 应该是 **1**。

## E. 行为异常排查（不是配置错）

> 这一类最容易误判成"配置写错了"。**先排除外部因素，再怀疑参数。**

### E-1 Nav2 反复 `Failed to make progress`，恢复次数耗尽后 ABORT

- **问题**：发目标 `(-4.5, 1.5)` 时，Nav2 反复报错并最终放弃，车停在中途不动。
- **现象**：

  ```text
  [controller_server]: Failed to make progress
  [controller_server]: [follow_path] [ActionServer] Aborting handle.
  ```

  `number_of_recoveries` 一路涨到 13~15，最后 `error_code: 105` 且
  `Goal finished with status: ABORTED`；车停在 `(-8.88, -0.55)`。

- **原因**：**不是配置 bug，是「临界 + CPU 争抢」导致的概率性失败。**
  同一份起点/目标，实测**既出现过 5 次恢复就成功（`error_code: 0`、距目标 0.23 m）**，
  **也出现过 15 次恢复后 ABORT**。

  逐项排除如下（每条都有实测证据）：

  | 怀疑对象 | 怎么验的 | 结论 |
  | --- | --- | --- |
  | 车物理被卡住 | 在它停下的位置手动发 `0.25 m/s` → 车走了 **1.16 m**；激光正前方 2.02 m 无障碍 | ❌ 排除 |
  | AMCL 定位飘了 | `/amcl_pose` 与 `gz model -p` 真值逐点对比，全程偏差 **1~3 cm** | ❌ 排除 |
  | `collision_monitor` 压速度 | 它全程只打了启动横幅，之后再无任何消息 | ❌ 排除 |
  | 速度链上某级吃掉指令 | 同时录 `/cmd_vel_nav`、`/cmd_vel_smoothed`、`/cmd_vel`，三级**完全一致**（都 47% 非零、范围都是 `[0, 0.26]`） | ❌ 排除 |
  | 目标几何上不可达 | `tools/map_reachability.py`：最宽路线最窄处半径 **0.750 m** ≫ 车半径 0.22 m | ❌ 排除 |
  | 仿真太慢导致 10 秒窗口不够 | RTF ≈ **1.00**；`use_sim_time` 全为 `True`；progress checker 两参数未设 = 默认 10 s / 0.5 m | ❌ 排除 |

  **`Failed to make progress` 本身报得没错**，它是症状不是原因 ——
  把报错时刻和真实位置对齐，10 秒位移实测 0.16 / 0.05 / 0.00 / 0.01 m。

  唯一站得住的相关因素：**同期的 Nav2 自己报了控制环性能不足**：

  ```text
  [controller_server]: Control loop missed its desired rate of 20.0000 Hz.
                       Current loop rate is 5.7471 Hz.
  [planner_server]:    Planner loop missed its desired rate of 20.0000 Hz.
                       Current loop rate is 1.3605 Hz.
  ```

  控制环只有配置值（20 Hz）的 1/3~1/4，DWB 的轨迹采样与打分质量必然下降。

- **解决**：
  - 跑 Nav2 相关验证时**不要同时开 rviz / Gazebo GUI**，先把 CPU 让出来；
  - 复现/观察：`bash tools/run-stuck-repro.sh`
    （瞬移回起点 + 按真值对齐 AMCL + 同时录整条速度链，一遍看完）；
  - **不要**为了这个去改 Nav2 参数 —— 参数本身没问题，是资源不够。

### E-2 「只打日志说明」的噪声：`Failed to transform initial pose in time`

- **问题**：设 AMCL 初始位姿时几乎必打这行警告，看着像失败了。
- **现象**：

  ```text
  [amcl]: Failed to transform initial pose in time (Lookup would require
    extrapolation into the future.  Requested time 1923.414000 but the latest
    data is at time 1923.405000, when looking up transform from frame
    [base_footprint] to frame [odom])
  ```

- **原因**：`odom→base_footprint` 这条 TF 比仿真时钟滞后约 0.2~0.3 s
  （`/odom` 是 50 Hz，但 TF 时间戳落后于 `/clock`）。
- **解决**：**不用管**。实测三种时间戳策略后 `/amcl_pose` 与真值的偏差分别是
  0.016 m / 0.053 m / 0.036 m，位姿都确实生效了；而且设定前 AMCL 一直在打
  `AMCL cannot publish a pose or update the transform. Please set the initial pose...`
  （= 没有位姿），设定后立刻正常发布 `map→odom`。
  **不要为了消这行日志去调时间戳，那是白费功夫。**

### E-3 设初始位姿用了墙上时间，AMCL 不认

- **问题**：发了 `/initialpose` 但 AMCL 不更新位姿。
- **现象**：`/amcl_pose` 不出新值、`map→odom` 不发布，AMCL 持续打
  `AMCL cannot publish a pose or update the transform. Please set the initial pose...`。
- **原因**：仿真里 AMCL 用**仿真时间**（`use_sim_time: True`），
  而初始位姿消息带的是墙上时间戳，对不上。
- **解决**：`use_sim_time=True`，且时间戳置 **0**（让 tf2 取最新可用变换）。
  已固化在 `tools/set_initial_pose.py` 里，支持 `--from-gz` 直接对齐真值。

### E-4 「绕远路」不是 bug

- **问题**：目标直线距离 6.68 m，Nav2 却报 `distance_remaining` 18.17 m。
- **现象**：规划出来的路径明显绕远，接近直线的 3 倍。
- **原因**：navfn 默认 `use_astar: false`，是**按代价最小**而不是距离最短找路；
  膨胀层（`inflation_radius`）会给墙附近一大片格子加代价，如果直线全程贴着墙，
  它的累计代价可能高于一条更长但更空旷的路。
- **解决**：确认车确实能走直路之后，调小 `inflation_radius`（0.55 → 0.3 左右）
  或 `cost_scaling_factor`。
  排查手法：`python3 tools/map_clearance.py --from 2.17 1.88 --to -4.5 1.5`。
- **⚠️ 本条原来还写过一句「或把 `use_astar` 改成 `true`」—— 2026-10-03 实测证伪**：
  A* 与 Dijkstra 走的是**几乎同一条路**（18.50 vs 18.40 m，代价 924.9 vs 920.0），
  因为它们最小化的是同一个代价函数、最优解相同。完整数据见 **E-16**。
- **🔬 补充（2026-10-03）**：本条原来的措辞「确认车确实能走直路之后」容易被误读 ——
  实测这条直线在 `x≈-2.12` 处离墙只有 **0.05 m**，**根本不可行**。
  所以本例的正确说法是「**车走不了直路，绕行是对的**」；
  至于「车能走直路却绕行」那种情况，定量判据也在 E-16 里。

### E-5 里程计漂移（`open_loop: true`）

- **问题**：巡逻一圈后 `/odom` 与真值差很多，看起来像定位坏了。
- **现象**：实测一圈后 `/odom` 报 `(3.58, 6.16) yaw ≈ −168°`，
  而真值是 `(4.57, −1.17) yaw ≈ 154°`，差了 7 m / 38°。
- **原因**：`mybot_ros2_controller.yaml` 里 `open_loop: true`，
  里程计**按"指令速度"积分，不看轮子实际转了多少**；仿真里原地转向时轮子会打滑，
  这部分打滑里程计完全看不到。
- **解决**：**不是 bug，真机也一样** —— 这正是必须要 AMCL / 建图的原因。
  AMCL 会把它纠正回来，所以导航到位误差仍只有 0.2 m 级。
  想直观感受：对比 `tf2_echo map base_footprint`（已纠正）和
  `ros2 topic echo /odom`（未纠正）。
- **⚠️ 补充（2026-10-03）**：本条只解释「odom 为什么会漂」这个**机理**，
  **不要**据此推断「把 `open_loop` 改成 `false` 就能治好漂移」——
  实测改成 `false` 后 odom 误差反而从 16.5 m 涨到 19.97 m（见 E-13 的对照表）。

### E-8 相机帧率只有 3~4 Hz

### E-9 遥控结束后容器里残留 `mybot_teleop.py`，机器人“没人碰却在动”

- **问题**：结束遥控后，容器里仍有 `mybot_teleop.py` 在跑，并继续按最后一条指令发布 `/cmd_vel`。
- **现象**：`./scripts/stop-sim.sh` 报「剩余仿真相关进程：0」，但
  `./scripts/shell.sh -c "pgrep -af mybot_teleop"` 仍能看到
  `python3 /workspace/my-slam/src/robot/mybot_description/scripts/mybot_teleop.py --forward`；
  `ros2 topic info /cmd_vel` 显示 **Publisher count: 1**。
  本次仿真已停所以暂时没人受害 —— 但**一重启仿真，机器人会立刻按 0.2 m/s 冲出去**。
- **原因**：`teleop.sh` 确实写了兜底 —— `trap cleanup INT TERM EXIT`，`cleanup()` 在容器里
  `pkill -f mybot_teleop.py`，还专门用 `CEXEC_NO_EXEC=1` 保证 EXIT trap 有机会跑。
  但 **SIGKILL 不触发任何 trap**：用“直接强杀终端/进程”的方式结束遥控时，cleanup 根本不会执行。
  本次就是这样（我用的是强杀，不是 Ctrl-C）。
  另外 `stop-sim.sh` 只管仿真进程，**不负责** teleop 残留
  （图形工具另有 `./scripts/stop-gui.sh`，而 teleop 由 `./scripts/stop-teleop.sh` 负责）。
- **解决**：
  1. 结束遥控请用 **Ctrl-C**（触发 INT → cleanup），不要强杀终端。
  2. 事后清理用 **`./scripts/stop-teleop.sh`**：模式写在脚本文件里避开 F-7，
     内部直接用 `kill -9` 避开 F-12。
  3. ✅ **已实测确认** `cleanup()` 用的信号是够的：单独 `kill -TERM <pid>` 后
     `mybot_teleop.py` 在 3 秒内自行退出（不受 F-12 那个「rqt 忽略 SIGTERM」的影响）。
     所以 Ctrl-C 路径下 trap 确实有效，问题**只**出在 SIGKILL 上。

### E-12 ROS `/clock` 的发布者是 **2**（gz 在两个话题名下发时钟）

- **问题**：拿「发布者必须为 1」去量 `/clock`，会得到误报。
- **现象**：`ros2 topic info /clock -v` 显示 **Publisher count: 2**，
  两个端点**都叫 `ros_gz_bridge`**；`ros2 topic hz /clock` 约 **1970 Hz**。
- **原因**：gz 把时钟**同时**发在 `/clock` 和 `/world/<world>/clock` 两个话题名上
  —— 实测两个话题的**发布者地址完全相同**，说明是同一个源：

  ```text
  $ gz topic -i -t /clock                -> tcp://172.25.0.2:46819, gz.msgs.Clock
  $ gz topic -i -t /world/default/clock  -> tcp://172.25.0.2:46819, gz.msgs.Clock
  ```

  而 `gazebo_sim_gz.launch.py` 为兼容「时钟只在世界命名空间下发」的旧行为，
  在 `CLOCK_TOPIC_TEMPLATES` 里**把两条都桥了**，再统一重映射到 ROS 的 `/clock`。
  既然 gz 侧两边都有数据 → **两条桥都在转发** → ROS `/clock` 就出现了两个发布者。
- **⚠️ 附带发现**：launch 文件注释里那条前提
  （`gz topic -i -t /clock` → `No publishers on topic [/clock]`）
  **现在已经不成立**了。注释原本假设「两条里必有一条没数据、会自然闲置」，
  实测**两条都有数据**。
- **影响**：**功能正常** —— `use_sim_time` 拿到的是正确时间。
  只是「发布者必须为 1」这条判据**不适用于 `/clock`**。
  好消息：`tools/check_topic_health.sh` 检查的 7 个话题里**不含 `/clock`**，
  所以已有的验证结论没有被推翻。
- **解决**：**不改代码**。功能正常，改了要重跑一遍全部验证，收益很小，
  只需记住判据不适用。真要消掉，把 `CLOCK_TOPIC_TEMPLATES` 里的第二条
  `/clock@...` 删掉即可，让 ROS `/clock` 的发布者数回到 1。

### E-13 建图时 SLAM 发散 —— 根因是机器人被卡住，不是算法、也不是 `open_loop`

- **问题**：让机器人自动巡航「走全覆盖」建图，走到一半 SLAM 位姿就和真值差了十几米，
  存出来的地图比房间大一倍；但同一条路径换成小范围绕圈就完全正常。
- **现象**：三个可复现的观察。
  1. **真值列会「冻结」**。日志里 Gazebo 真值（`gz model -m mybot -p`）
     连续十几个航点一动不动，说明机器人物理上根本没动：

     ```
     [ 10/56] 到位  真值( -7.20, -1.70)  odom误差 1.05  SLAM误差 0.03   ← 还在走
     [ 11/56] 到位  真值( -7.23, -2.52)  odom误差 0.74  SLAM误差 0.77   ← 到达，停下
     [ 12/56] 到位  真值( -7.21, -2.52)  odom误差 2.42  SLAM误差 2.38   ┐
     [ 16/56] 到位  真值( -7.24, -2.52)  odom误差 6.53  SLAM误差 4.86   ├ 真值冻结
     [ 21/56] 放弃  真值( -7.28, -2.52)  odom误差 2.16  SLAM误差 0.99   ┘ 13 个航点
     ```

     注意 **SLAM 误差是跟着 odom 误差涨的，不是自己先涨**。
  2. **发散后地图会「膨胀」**。房间真值 18.8 × 11.1 m，两张发散图分别量到
     20.7 × 20.6 m 和 27.6 × 21.2 m。
     **最灵敏的判据是「障碍格的世界包围盒」**：

     | 地图 | 障碍包围盒 | 与教材图一致率 | 只有我有障碍 / 只有你有障碍 |
     | --- | --- | --- | --- |
     | 正常 | **18.7 × 11.0 m** | **96.9%** | 442 / 2110 |
     | 发散 | **19.9 × 17.2 m** | 92.8% | 2762 / 2660 |

     发散图两侧数量相当 —— 这是**幽灵障碍**的签名（凭空多出障碍、又漏掉真的障碍）。
  3. **假设被实验否定**：曾怀疑是 `open_loop: true`（odom 按指令速度积分，看不到打滑）。
     只改这一个参数重跑，结果**更差**：

     | | `open_loop=true` | `open_loop=false` |
     | --- | --- | --- |
     | odom 误差 | 16.5 m | **19.97 m** |
     | SLAM 误差 | 11 m | **18.68 m** |
     | 地图高度 | 20.6 m | **21.2 m** |

- **原因**：**卡死 → 打滑 → odom 漂 → SLAM 先验坏**，链条如下（每步都有上面的数据支撑）：
  1. 测试脚本是纯贪心「朝目标直发速度、不看障碍」。两个**各自净空都合格**的航点
     （`(-7.20,-1.88)` 净空 0.80 m、`(-7.20,-3.48)` 净空 0.45 m，相距 1.6 m）
     之间的**直线路径要穿过一道 y≈-2.7 的家具** → 机器人笔直撞上去卡死。
     **航点净空 ≠ 路径净空。**
  2. 卡住后控制器仍在发速度指令，**轮子空转打滑** → odom 继续累积
     （误差 1.05 → 6.53 m）。
  3. SLAM 用这个错的 odom 当**运动先验** → 先验太离谱 → 扫描匹配失败 → 位姿漂走。
  4. 漂走的位姿让贪婪控制器误判「到位」/ 朝错方向走 → 第二次撞墙 → 正反馈。

  `open_loop` 之所以**不是**那个变量：打滑时轮子转速也**确实非零**，
  `false`（读轮子实测转速）会忠实地把打滑积进去，`true`（按指令速度积分）同样会漂。
  **两种设置都救不了打滑。**
- **解决**：给驾驶脚本加上避障（见 `tools/map_coverage.py`，四层保护：
  逐像素净空选点 + 地图 BFS 路径规划 + `/scan` 安全网 + 卡死脱困）。
  **同一条参考路线重跑，odom 误差照样涨到 2.49 m，但 SLAM 误差全程 0.04~0.09 m
  从没发散**，地图包围盒回到 18.7 × 11.0 m。因果链闭环。
- **附带结论（正面）**：正常行驶时 **SLAM 误差 0.01~0.09 m，比 odom 误差（可到 1.05 m）还小**
  —— 这就是 slam_toolbox 的扫描匹配在修正 odom 漂移的直接证据。
- **教训**：**「SLAM 发散」是果不是因。** 在建图/导航里看到定位飘，
  先问「机器人当时真的在动吗」，再去怀疑算法。
  判据组合：**真值冻结 + odom 误差单调涨 + SLAM 误差跟着涨**。

### E-15 生效的内切半径比配置的 `robot_radius` 大 4.9 mm

- **问题**：想用 `robot_radius` 算「门要多宽才能过」，但按配置值算出来的结论
  和实测代价地图对不上。
- **现象**：用 `tools/probe_costmap.py` 从代价地图**反推**有效内切半径
  （由 `实测代价 = 252·exp(-csf·(d − r))` 解出 `r = d + ln(实测/252)/csf`）：

  | 代价地图 | 致命格 | 反推 `inscribed_radius` |
  | --- | ---: | ---: |
  | `global_costmap` | 3475 | **0.2249 m** |
  | `local_costmap` | 34 | **0.2248 m** |

  8 个独立距离桶给出的值落在 `0.2238 ~ 0.2254`，**稳定**，不是噪声。

  而配置里 `robot_radius` = **0.22**，已在运行节点上复核：
  `ros2 param get /global_costmap/global_costmap robot_radius` → `Double value is: 0.22`；

  本次的 `tools/probe_costmap.py`（反推内切半径）。

### E-16 全局规划器最小化的是「代价」不是「距离」（定量版）

> 这是 E-4 的定量化。E-4 当时只有定性解释，而且其中一条「解法」是错的（见文末）。

- **问题**：起终点直线距离 6.68 m，Nav2 给出 18.4 m 的路径，接近 3 倍。
- **现象**：用 `tools/probe_planner.py` 对 `(2.17, 1.88) → (-4.50, 1.50)` 量三组数据。
  代价按 navfn 的模型算（`navfn.hpp`：`COST_NEUTRAL 50` + `COST_FACTOR 0.8`；
  `costmap cost ≥ 253` 视为障碍）：

  | 路线 | 长度 | 代价积分 `∫(50+0.8·cost)ds` | 沿途最高导航代价 |
  | --- | ---: | ---: | ---: |
  | 直线 | 6.68 m | —（不可行） | **253.0**（`x≈-2.12` 处离墙仅 0.05 m） |
  | **只按距离找路**（自算对照组） | **17.60 m** | **3383.0** | **253.0**（不惜贴墙） |
  | **navfn 实际输出** | **18.50 m** | **924.9** | **50.0**（全程纯开阔地） |

  navfn 多绕 **0.9 m**，代价降 **2458（−72.7%）**。
- **决定性旁证**：navfn 输出的**沿途最高导航代价 = 50.0**，正好等于 `COST_NEUTRAL` ——
  也就是**它全程只走 `costmap cost = 0` 的格子**，一点膨胀代价都不沾。
  这是「代价驱动」最干净的指纹。
- **原因**：navfn 在代价图上跑 Dijkstra，累加的是每格的导航代价，不是距离。
  `navfn.hpp` 的注释还解释了 `COST_FACTOR` 为什么取 0.8：
  > 若取值更大，障碍周围会出现「代价高原」，规划器会认为整条窄走廊一样不可取，
  > 从而**不会沿走廊中线规划**。
- **解决**：**不用解决** —— 绕行是正确行为，因为直线**根本不可行**
  （`tools/map_clearance.py` 独立复核：最小离墙 0.05 m，5/15 个采样点在膨胀区内）。
- **⚠️ 本条纠正了 E-4 里一句错话**：E-4 建议「或把 `use_astar` 改成 `true`」。
  实测 A/B（同一对起终点，只改这一个参数，通过 `params_file:=/tmp/tune.yaml` 重启 Nav2）：

  | `use_astar` | 路径点数 | 长度 | 代价积分 |
  | --- | ---: | ---: | ---: |
  | `false`（Dijkstra） | 735 | 18.40 m | 920.0 |
  | `true`（A*） | 739 | **18.50 m** | **924.9** |

  **差 0.5%，基本是同一条路**（而且 A* 略长，不是略短）。
  原因：navfn 的 A* 启发式是**可采纳**的（所有格子导航代价 ≥ `COST_NEUTRAL`），
  与 Dijkstra 最小化的是同一个代价函数 → 最优解相同。
  `use_astar` 影响的是**搜索开销**，不是路径形状；本图只有 83k 格，开销差异测不出来。
  **真正的旋钮是 `inflation_radius` / `cost_scaling_factor`**，前提是那条缝真过得去。
- **测量工具**：`tools/probe_planner.py`（自带「只按距离找路」对照组 + 直线代价剖面）。

### E-17 DWB 是「采样式」局部规划器 —— 候选数公式 + `scale` 生效律

- **问题**：DWB 有 40 个参数，看起来像一堆魔法数字。想知道「它到底在干什么、
  为什么这一周期选了那个速度」。
- **现象**：DWB 把**每条候选轨迹的完整评分**发在 `/evaluation` 上
  （`dwb_msgs/msg/LocalPlanEvaluation`，本项目 `publish_evaluation` 默认为 `True`）：

  ```text
  LocalPlanEvaluation
    TrajectoryScore[] twists     # 全部候选
      Trajectory2D traj.velocity # (x, y, theta)  即 (v, v_y, ω)
      CriticScore[] scores       # name / raw_score / scale
      float32 total
    uint16 best_index            # 选中那条的下标
    uint16 worst_index
  ```

  实测选中那条的明细（选中 `v=0.246, ω=0.000`，前推 11 个点 / 1.70 s = `sim_time`）：

  | critic | raw_score | scale | raw×scale |
  | --- | ---: | ---: | ---: |
  | RotateToGoal | 0.00 | 32.000 | 0.00 |
  | Oscillation | 0.00 | 1.000 | 0.00 |
  | BaseObstacle | 0.00 | 0.020 | 0.00 |
  | GoalAlign | 18.00 | **0.600** | 10.80 |
  | PathAlign | 0.00 | **0.800** | 0.00 |
  | PathDist | 0.00 | **0.800** | 0.00 |
  | GoalDist | 20.00 | **0.600** | 12.00 |
  | **合计** | | | **22.80** |

  **两条断言都成立**（可证伪，工具每次都自检）：
  `best_index == argmin(total)`、`total == Σ(raw_score × scale)`（差 < 1e-6）。
- **结论 1：候选轨迹条数 = `vx_samples × (vtheta_samples + 1) − 1`**

  | `vx_samples` | `vtheta_samples` | 实测候选数 | 公式 |
  | ---: | ---: | ---: | --- |
  | 20 | 20 | **419** | 20×21−1 = 419 ✅ |
  | 10 | 20 | **209** | 10×21−1 = 209 ✅ |

  θ 网格比 `vtheta_samples` **多一个「不转」**；`vy_samples: 5` **完全不参与**
  （差速车没有 y 自由度）。
- **结论 2：`MapGridCritic` 家族的生效 `scale` = 配置值 × `resolution` / 2**

  这个不是配置错误，是**运行时的单元换算**。用实验逐个排除出来的：

  | # | 改什么 | `GoalAlign`（配置 24.0）生效 scale | 否证了什么 |
  | --- | --- | ---: | --- |
  | 基线 | — | 0.600 | — |
  | ① | `GoalAlign.scale` 24→12、`PathAlign.scale` 32→64 | 0.3 / 1.6 | 确认与配置**成正比**（÷40） |
  | ② | `angular_granularity` 0.025→0.05 | 0.600 不变 | ❌ 不是它 |
  | ③ | `vx_samples` 20→10 | 0.600 不变 | ❌ 不是 `2×vx_samples` |
  | ④ | `linear_granularity` 0.05→0.1 | 0.600 不变 | ❌ 不是它 |
  | ⑤ | **`local_costmap.resolution` 0.05→0.025** | **0.300** | ✅ **是它**（÷80） |

  `libdwb_critics.so` 确实引用了 `nav2_costmap_2d::Costmap2D::getResolution()`。
  `RotateToGoal` / `Oscillation` / `BaseObstacle` **不受此影响**，就是配置值。
- **影响**：调 `PathAlign.scale` / `GoalAlign.scale` 这类参数时，要知道它在 `res=0.05`
  下被除了 40 —— **配置里写 32，实际只相当于 0.8**。
  所以「把 scale 从 32 调到 35」这种微调几乎不可能看出效果。
- **⚠️ 那个 `/2` 的来历未定位**（可能是半格偏移，或 cell→meter 的换算约定）。
- **测量工具**：`tools/probe_dwb.py`（自己发导航目标 + 解析 `/evaluation` + 两条断言自检）。

### E-18 Nav2 起不来：`planner_server` 因拿不到 `map` 帧而激活失败，整条链中止

- **问题**：`ros2 launch mybot_navigation2 navigation2.launch.py` 启动后，
  一半节点停在 `inactive`，导航完全不能用。
- **现象**：日志里三连：

  ```text
  [global_costmap]: Timed out waiting for transform from base_link to map
                    tf error: Invalid frame ID "map" ... frame does not exist
  → Failed to change state for node: planner_server
  → Failed to bring up all requested nodes. Aborting bringup.
  ```

  `global_costmap` 的 `global_frame` 是 `map`，而 `map` 帧**由 AMCL 发布** ——
  而 AMCL 要**先拿到初始位姿**才会发 `map→odom`。所以没人设初始位姿时，`map` 帧不存在。
- **原因**：`global_costmap` 的 `initial_transform_timeout`（**实测 60.0 s**）超时后放弃，
  `planner_server` 激活失败，`lifecycle_manager_navigation` 就**中止整条链**。
  中止之后再调 `manage_nodes` 只会返 `success=False` —— **必须重启，不能补救**。
- **解决**（两条都行）：
  1. **用 `bringup_sim.launch.py`** —— 它的 `pose_delay=30.0` 正好落在 60 秒窗口内，
     会自动调 `init_robot_pose`。**单独起 `navigation2.launch.py` 没有这一步。**
  2. 单独起 `navigation2.launch.py` 时，**60 秒内**手工跑
     `python3 tools/set_initial_pose.py --from-gz`。
- **这个坑在本次会话里反复出现**（做参数 A/B 要反复重启 Nav2），所以已固化成标准姿势：

  ```bash
  cp .../nav2_params.yaml /tmp/tune.yaml && sed -i '...' /tmp/tune.yaml
  ./scripts/stop-nav2.sh && 起 navigation2.launch.py params_file:=/tmp/tune.yaml
  sleep 27 && python3 tools/set_initial_pose.py --from-gz
  # 再跑测量工具
  ```

  好处：**源码 `nav2_params.yaml` 全程不动**（符合本仓库「实验不改源码」的约定）。
- **排查时不要被噪声带偏**：`Failed to transform initial pose in time` 只是「先报一条、后成功」
  的噪声（见 E-2），和本条不是一回事。
- **交叉引用**：`docs/详解-nav2_params.md` §13.2「场景 B：Nav2 起不来 / 一半节点 inactive」。

## F. 自己写分析脚本时踩的坑（方法论）

> 这一节记录的是**我（开发/分析方）自己的错误**，不是项目代码的错。
> 之所以单列，是因为最早那两条（F-1 / F-2）都差点导致"基于错误测量得出重大结论"。

### F-1 从 PGM 行号反推 y 时方向写反，整张图在 y 上被镜像

- **问题**：手写脚本扫描 `room.pgm` 时，把障碍的 y 坐标说错了。
- **现象**：报出“障碍在 y≈0.9”，实际位置在 y≈−5.2，差了约 6 m；
  并据此写了一整段错误推理。
- **原因**：**PGM 的首行对应 y 最大值**，正确换算是
  `row = h - 1 - int((y - oy) / res)`。但是遍历时按这个公式取行、
  却用 `y0 + i * res` 去标注行号，标签和真实 y 就差了一个镜像。
- **解决**：
  - **不要手写扫描脚本**，用已验证的工具：
    `tools/map_reachability.py`、`tools/map_clearance.py`
    （这两个的行列换算都验证过）；
  - 真要自己写，先拿一个**已知点回代**验证。

### F-2 占用判据和 `map_server` 不一致，凭空造出一大片墙

- **问题**：把 `room.pgm` 的中间灰度当成障碍，得出了假的“目标不可达”结论。
- **现象**：按错误判据会在地图上多出一大片不存在的墙；同一目标另一次运行又能到达，
  说明结论不自洽。
- **原因**：`room.yaml` 是 `mode: trinary`，`occupied_thresh=0.65`、
  `free_thresh=0.25`，`map_server` 按 `occ = (255 − pixel) / 255` 判断：

  | pixel | occ | 判定 | 本图占比 |
  | --- | --- | --- | --- |
  | 0 | 1.000 | **障碍** | 3463 px |
  | 205 | 0.196 | **自由** | 3157 px |
  | 254 | 0.004 | **自由** | 76852 px |

  **205 是自由空间，不是"未知区域"**。把它当障碍，地图上就会多出一大片
  不存在的墙。

- **解决**：判禁用 `pixel <= 100`（等价于 `occ > 0.65`），
  或直接用 `tools/map_reachability.py`（判据写在文件开头的说明里）。
  **自检技巧**：故意放一个"预期不可达"的输入做对照实验
  —— 例如 `(4.5, 1.5)` 那格是 `cafe_table_1`，脚本正确报"不可达"，说明方法可靠。

### F-3 `set -u` 会让 `source ROS 的 setup.bash` 静默把脚本打掉

- **问题**：分析脚本跑起来没有任何反应。
- **现象**：脚本“没有任何输出、退出码 1”，看着像逻辑错误。
- **原因**：ROS 的 `setup.bash` 会引用未定义变量，在 `set -u` 下会直接终止当前 shell；
  而脚本里又写了 `source ... >/dev/null 2>&1`，把报错一起吞了，于是表现为"什么都没发生"。
- **解决**：不要在 `source setup.bash` 之前开 `set -u`（或干脆不用）。
  本仓库的脚本按此约定：**先用 `source`，再考虑其它 shell 选项**。
- **又踩了一次（2026-10-02）**：写 `tools/walk_mybot_description*.sh` 时
  下意识写了 `set -uo pipefail`，于是**再次**得到「无输出、退出码 1」，
  和当初一模一样。所以这条不是理论风险，是**会反复犯**的。
  自查方法：脚本里出现 `set -u` 时，确认它**不在** `source` 之前。

### F-4 `ros2 topic echo` 走管道时输出会被整体缓存

- **问题**：用 `ros2 topic echo` 叠加管道做时序记录时，时间戳全部失效。
- **现象**：所有记录的时间戳**都一模一样**（都等于最后一条的时间）。
- **原因**：管道里 `ros2 topic echo` 的输出被整体缓冲，下游（awk / while read）
  只在进程结束时才一次性收到全部数据。
- **解决**：需要"带时间戳的时序记录"时，**用 rclpy 写订阅者**自己打时间戳
  （见 `tools/probe_cmd_chain.py`、`tools/probe-localization-vs-truth.sh`），
  不要指望 `echo | 管道`。

### F-5 嵌套引号把 heredoc 搞坏

- **问题**：多层嵌套的命令行怎么都跑不起来。
- **现象**：`docker ... bash -lc '... python3 - <<"PY" ... PY'` 报
  `zsh: no matches found: ...`，命令整段没执行。
- **原因**：内层 Python 代码里含有**单引号**（例如
  `'障碍' if x else '自由'`），把外层的单引号提前闭合了。
- **解决**：这种多层的命令不要硬凑，**写成脚本文件**再调用
  （本仓库 `tools/` 下的一堆脚本就是这么来的，同时也方便复用和 review）。

### F-6 长驻命令不要接 `head`

- **问题**：用 `head` 截断长驻命令，会得到“话题挂了”的假结论。
- **现象**：`timeout 12 ros2 topic hz /scan | head -1` 输出
  `topic [/scan] does not appear to be published yet`，看起来像话题挂了。
- **原因**：管道提前关闭导致上游命令报假错误。实际上 `/scan` 好好的
  （`ros2 topic info /scan` 显示 Publisher count: 1，实测 9.99 Hz）。
- **解决**：不要用 `head` 截断长驻命令；用 `ros2 topic echo --once` 验证。

### F-7 `pkill -f` 会杀掉自己

- **问题**：清理进程的脚本会把自己也杀掉。
- **现象**：脚本执行后立即结束，看不到任何输出。
- **原因**：`pkill -f 'navigation2.launch.p[y]'` 里的模式能匹配到**同一条命令行
  后半段**的字面量，于是 pkill 把自己的 shell 也杀了。（踩过两次。）
- **解决**：把 pkill 模式**放进脚本文件**（`tools/stop-nav2-patrol.sh`、
  `tools/stop-sim.sh`），杀进程那条命令行里只出现脚本路径，不可能自匹配。

**变体（第 3 次，不是杀自己而是杀调用者）**：

```bash
./scripts/shell.sh -c "pkill -f mybot_teleop.py; sleep 1; echo cleanup-done"
```

`cleanup-done` 一次都没打印 —— 因为容器里那个 `bash -c "..."` 的**命令行本身
就含 `mybot_teleop.py`**，pkill 匹配到它，把父 shell 杀了，于是再没走到 `echo`。
宿主机侧 `pkill -f "scripts/teleop.sh"` 同理。
**判断信号**：命令没报错、退出码也正常，但**后续语句没执行**。

**不想写脚本文件也能安全**：用字符类打断字面量，让模式匹配不到自己的命令行 ——

```bash
pgrep -f 'mybot_teleop[.]py'   # 自己的命令行里是 [.]，而正则要求的是字面的 .
pkill -f 'mybot_teleop[.]py'   # 同理，不自匹配
```

命令行里只要出现**完整字面量**就会被匹配，所以在命令行里临时用 pkill 时优先这种写法；
要长期复用的仍然放进脚本文件。

### F-8 `ros2 action list` 读的是 daemon 缓存

- **问题**：想用它判断 Nav2 是否还活着，结果不准。
- **现象**：节点已经退出（或还没起来），它仍然能把 action 列出来。
- **原因**：它读的是 ROS daemon 的发现缓存，不是实时状态。
- **解决**：不能用来判断节点存活。要看进程用 `pgrep`，
  要看话题通不通用 `ros2 topic info --verbose`。

### F-9 把「无法复现的故障」归因成「上游缺陷」

- **问题**：一轮排查没定位到原因，就把结论写成「上游 arm64 构建缺陷」，
  并据此写了文档、定了架构（改用自研桥绕开）。
- **现象**：这个结论写进了 README、launch 注释和自研桥源码头部，并被当成
  “已确认”引用；过了一天（换了个时间点、什么都没改）**全部复现不出来**。
- **原因**：犯了两个错 ——
  1. 把**观测**当成了**解释**。「同一份参数连跑 3 次失败集合相同」是观测；
     「所以是上游库的缺陷」是解释，中间那一步没有证据。
  2. 用了一个**本身不可靠的取证手段**（Release 构建下按 ABI 从寄存器取函数参数），
     就把它当成“最硬的证据”。
- **解决**：
  - 严格区分「观察到什么」和「为什么」，后者没证据就写**未定位**；
  - 排除法只能得出“**不是**这些原因”，**不能**推出“就是那个原因”；
  - 下结论前先问一句：**换个时间点还能复现吗？** 复现不了的故障不要写成结论。
  - 已撤回的 3 处：README 对应小节、launch 注释、`gz_sensor_bridge_node.cpp` 文件头。

### F-10 `git mv A dir/` 在 `dir` 不存在时是「重命名」，不是「移入」

- **问题**：把 22 个包分到 4 个子目录时，4 个包被**改了名**，还把其他包嵌套进了包内部。
- **现象**：`src/robot` 里装的直接是 `mybot_description` 的内容（`urdf/`、`world/`…），
  而 `mybot_bringup`、`gz_sensor_bridge` 被塞进了这个包目录里；
  `src/navigation` = 旧 `mybot_navigation2`、`src/app` = 旧 `mybot_application`、
  `src/learning` = 旧 `learn_compose`。
- **原因**：`git mv 源 目标目录/` 只有**目标目录已存在**时才移入；不存在时按「重命名」处理，
  **不会自动建目录**。第一次执行 `git mv src/mybot_description src/robot/` 真的是把包
  改名成了 `robot`，之后几条才变成“移入”。
- **解决**：目标写成**完整路径**（`git mv src/pkg src/group/pkg`），或先 `mkdir -p src/group`。
  已经错了的话，用显式路径修：先把被吐进来的包挪到暂存目录，把组目录名改回包名，再逐个放进组里。

### F-11 zsh 不对未加引号的变量做单词切分

- **问题**：用 `for p in $PKG_LIST` 批量移动包，循环只跑了一次且报 `bad source`。
- **现象**：`git mv "src/learning/$p" ...` 报
  `fatal: bad source, source=src/learning/learn_dds_cpp learn_executor_cpp ...`
  —— 整串被当成了**一个**路径。
- **原因**：**zsh 默认不做 word splitting**（bash 会）。`$PKG_LIST` 展开后仍是单个词，
  `$(find ...)` 的输出同理。
- **解决**：改为逐条写显式路径（本次采用）、或用 zsh 数组 `pkgs=(a b c)`、
  或显式开启切分 `${=PKG_LIST}`。写「批量操作一批路径」的脚本时优先用**数组**。

### F-12 `pkill -f` 返回 0 不等于杀掉了 —— SIGTERM 可能被忽略

- **问题**：清理进程时 `pkill -f <模式>` 返回 0，但目标进程根本没退出。
- **现象**：补测三个 GUI 包装脚本（`rviz2.sh` / `rqt.sh` / `gazebo.sh`）时，
  `rviz2` 用 `pkill -f 'rviz[2]'` 一次就清掉，而 `rqt` 连杀两次都还在 ——
  两次 `pkill` **都**返回 `exit=0`：
  ```text
  pkill -f "bin/rq[t]"; echo $?   -> 0
  pgrep -f "bin/rq[t]"            -> 2313 /usr/bin/python3 /opt/ros/jazzy/bin/rqt
  ```
- **原因**：`pkill` 的退出码只表示「**信号有没有发出去**」，**不表示进程已终止**。
  而 `rqt`（Qt 应用）**不理会 SIGTERM** —— 实测单独 `kill -TERM 2313` 同样返回 0，
  2 秒后进程依旧在。默认的 `pkill` 发的是 SIGTERM，所以对它无效。
- **解决**：对 GUI 类进程用 `pkill -9 -f`（实测一次清掉）。
  更重要的是：**不要拿 `pkill` 的退出码当「已清理」的证据**，
  要随手 `pgrep` 复核一遍。本次三个 GUI 的实测结论：
  `rviz2` 响应 TERM；`gz sim`（server + gui）自己会退；
  `rqt` **必须 KILL**。
- **与 F-7 叠加会更坑**：`pkill -f` 的自匹配问题在这条命令里又犯了一次 ——
  同一条命令里既写了 `echo "--- 杀 gz sim ---"`，又写了 `pkill -f "gz si[m]"`，
  echo 里的**字面量 `gz sim`** 让 pkill 把执行这条命令的 shell 一起杀了，
  输出就此中断。方括号只能防 pkill **自己**，
  防不住**父 shell 命令行里的同一串字面量**。

### F-13 数 gz 消息条数时数错字段 —— 一条消息里有 360 个同名值

- **问题**：想统计 gz 话题的实际频率，用
  `gz topic -e -t <话题> | grep -c <字段>` 数条数，得到离谱数字。
- **现象**：给雷达做「改 `update_rate` 10→20」的 A/B 验证时，下面这条命令
  给出 **约 7020 Hz**（期望 ~20 Hz）：

  ```bash
  n=$(timeout 3 gz topic -e -t /scan | grep -c 'ranges:')
  ```

  看着像「gz 雷达跑到 7 kHz」这种惊天 bug。
- **原因**：**一条 LaserScan 消息里有 360 个 range 值**，所以数 `ranges:` 得到的
  是消息数的 **360 倍**：`7020 / 360 ≈ 19.5 Hz`，正好是预期值。
- **第二次也没对**：换成 `grep -c 'frame_id:'` 想做交叉验证，返回 **0** ——
  gz 文本输出里那个字段的**名字不一样**，同样不是有效测量。
- **解决**：数「**每条消息只出现一次**」的字段。gz 话题的 header 里 `sec:` 可用：

  ```bash
  n=$(timeout 5 gz topic -e -t /scan | grep -cE '^ *sec:')   # -> 99 条 / 5 秒
  ```

  并且**用第二种独立方法对照**：ROS 侧 `ros2 topic hz /scan` 给 19.36 Hz，
  和 gz 侧的 19.8 Hz 互相印证，才敢下结论。
- **教训**：「**频率不对**」和「**数错了**」的现象**完全一样** —— 都是数字不对。
  先确认**测量本身有效**，再解释测量结果。
  本仓库已在 `tools/walk_mybot_description_step6.sh` 的注释里写进这条约定。

### F-14 卡死检测把「原地旋转」当成了「卡住」

- **问题**：给巡航脚本加「命令前进却不动 → 判卡死 → 脱困」的保护，
  结果刚开始跑就频繁误报，白白浪费脱困动作。
- **现象**：三次误报的 `err`（航向误差）分别是 **0.44 / 0.50 / 0.49** ——
  全都贴在转向阈值 `0.5` 下面；而且诊断打印的真值恰好是**起点和上一个航点**：

  ```
  [卡死] SLAM位姿( 0.00, 0.00) 真值(-0.00, 0.00) tv=0.150 goal_d=0.85 err=0.44 静置 3.9s
  [卡死] SLAM位姿(-0.66,-0.25) 真值(-0.65,-0.24) tv=0.150 goal_d=1.46 err=0.50 静置 3.6s
  ```

- **原因**：控制律是「`|err|>0.5` → 原地旋转（`tv=0`）」
  「`|err|<0.5` → 前进+转向（`tv=0.15`）」。
  **原地旋转时 `x,y` 本来就不变**，但卡死计时器的基准点没有重置。
  于是机器人转了几秒、刚把 `err` 转到 0.5 以下、**刚开始前进的那一瞬间**，
  基准点已经过期 3.7 s → 立刻误判卡死。
  `err` 聚在 0.5 附近就是这个机制的指纹。
- **解决**：基准点重置条件里加上「当前没在前进」：

  ```python
  if self.tv <= 0.0:            # 原地旋转/停车 → 重置基准
      ref = (px, py, time.time())
  elif ref is None:
      ref = (px, py, time.time())
  elif math.hypot(px - ref[0], py - ref[1]) > STUCK_D:
      ref = (px, py, time.time())
  elif time.time() - ref[2] > STUCK_T:
      return 'stuck'
  ```

- **教训**：**「没位移」要先分清是「不该动」还是「动不了」。**
  诊断这类问题最有效的一招是**把判据本身的中间量打出来**（这里是 `err`）——
  三次误报的 `err` 聚类立刻暴露了触发时机。

### F-15 安全网停距小于路径膨胀 → 把自己逼进「规划器认为的非法格」

- **问题**：巡航跑到一半，剩下的航点全部报告「无路径」，机器人再也不动。
- **现象**：连续二十多个航点输出一模一样：

  ```
  [ 14/46] 无路径  真值( -4.35, -5.51)  odom误差 0.79  SLAM误差 0.08
  [ 38/46] 无路径  真值( -4.35, -5.51)  odom误差 0.79  SLAM误差 0.08
  ```

  真值一动不动，**但 SLAM 误差只有 0.08 m** —— 定位好得很，是**规划**走不通。
- **原因**：两个距离没对齐：
  - `/scan` 安全网停距 `STOP_RANGE = 0.30 m`，而雷达在车体中心，
    所以机器人会开到**离墙 0.30 − 0.12（底盘半径）= 0.18 m**；
  - 路径规划的膨胀量是 `0.12 + 0.08 = 0.20 m`，于是「离墙 0.18 m」的那格
    在规划器眼里是**非法格**；
  - `plan()` 会校验起点合法性，起点非法 → 直接返回 `None` → 所有航点都规划失败。

  即：**安全网允许机器人开到「规划器认为不存在的位置」**，两边自相矛盾。
- **解决**：两条一起改。
  1. 停距必须 ≥ 底盘半径 + 路径膨胀：`STOP_RANGE = 0.40`；
     并加启动自检，`--stop-range` 小于该值时打印警告。
  2. `plan()` 加 `snap()` 兜底：起点非法时用 BFS 找最近的合法格再规划。
  3. 顺带把安全网扫描半角从 ±30° 放宽到 ±60°
     （只看正前方会在贴墙转弯时漏看两侧）。
- **教训**：**约束系统里每个「距离」都要对齐同一个基准。**
  「安全网」和「规划器」是两套独立的几何判断，谁都不能比对方更宽松 ——
  否则会出现「机器人合法地待在规划器认为非法的地方」这种自相矛盾的状态。

### F-16 看了代价地图的「压缩版」话题，把 253/254 读成了 99/100

- **问题**：想验证膨胀层的代价公式，从话题上取代价地图做逐格比对，结论全错。
- **现象**：取 `/global_costmap/costmap` 得到：

  ```
  min=0  max=100  不同取值数=35
  取值分布: 0×47843, 99×13885, 100×3470, 91×2426, 78×2128, 67×2072, ...
  ```

  「LETHAL(254) 有 0 格」—— 而这张全局代价地图覆盖整个房间，**满地都是墙**。
- **两次误判（都是自己造的）**：
  1. 先怀疑 `OccupancyGrid.data` 是 `int8[]`（**这是真的**，253→−3、254→−2、255→−1），
     于是加 `& 0xFF` 归一化 —— 但实测 `负值格数=0`，所以**这条对本次现象不成立**。
  2. 又去猜「是不是 0/100/−1 的 OccupancyGrid 约定」—— **也不对**，
     取值是 `0, 37, 43, 50, 58, 67, 78, 91, 99, 100`，是完整梯度，不是三值约定。
- **真正原因**：**同一份代价地图有两个话题，数字被改过**：

  | 话题 | 类型 | 内容 |
  | --- | --- | --- |
  | `<ns>/costmap` | `nav_msgs/msg/OccupancyGrid` | 真实代价**压缩到 0~100** |
  | `<ns>/costmap_raw` | `nav2_msgs/msg/Costmap` | **0~255 真实代价** |

  实测对照（两组数字的格数**一一对应**，证明确实是同一份数据）：

  | `*_raw` | 254 | 253 | 234 | 201 | 173 | 149 | 128 | 110 | 95 |
  | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
  | `/costmap` | 100 | 99 | 91 | 78 | 67 | 58 | 50 | 43 | 37 |
  | 格数 | 3470 | 13885 | 2426 | 2128 | 2072 | 2022 | 2058 | 2019 | 1819 |

  换成 `_raw` 之后：`max=254`，`LETHAL 254` 有 **3477 格**
  ≈ `room.pgm` 的 3463 个障碍格，全部对上。
- **解决**：验证代价相关的东西**一律用 `*_raw` 话题**（`nav2_msgs/msg/Costmap`）。
  工具已固化：`tools/probe_costmap.py` 默认就是 `_raw`，并按话题名自动判断类型。
- **教训**：这次的现象是「**数值范围不对**」，而**可能的原因至少有三个**
  （int8 符号 / OccupancyGrid 约定 / 话题本身被压缩）。
  我按顺序猜了两个错的，都是**用推理代替检查**。
  正确顺序是：**先 `ros2 topic list | grep costmap` 看看有几个话题、各自什么类型** ——
  一步就能定位，成本是 5 秒。

  > 这与 F-13（数错字段，频率差 360 倍）、F-2（占用判据不一致）是同一类：
  > **测量工具本身没验证过，后面所有结论都是空中楼阁。**

### F-17 又一次把行号方向搞反 —— 这次是在 `OccupancyGrid` / `Costmap` 上

- **问题**：新写的 `tools/probe_planner.py` 把「规划出来的路径」叠到代价地图上采样，
  报告「**规划路径居然撞障碍**」，而且长度只有 0.64 m（请求的是 6.68 m）。
- **现象**：

  ```
  ⛔ 直线上 (0.27, 1.77) 处撞到障碍
    规划路径 长度 0.64 m   代价积分 inf
  ```

  数字**自相矛盾**（路径撞障碍、长度荒谬），但**代码看起来完全正常**。
- **原因**：世界坐标 → 格号的换算，我照抄了 **PGM 的约定**：

  ```python
  r = h - 1 - int(round((y - oy) / res))   # ← 这是 PGM 的写法
  ```

  但 `nav_msgs/OccupancyGrid` 和 `nav2_msgs/Costmap` 的 `data` 是
  **「行 0 = origin 那一行（最小 y）」**，行号随 y **递增**，**不翻**：

  ```python
  r = int(round((y - oy) / res))           # ← 正确
  ```

  于是整张代价图在 y 上被**镜像**，采样点全落到了别处。
- **这是 F-1 的复发**：F-1 就是「从 PGM 行号反推 y 时方向写反，整张图在 y 上被镜像」。
  **同一类错误、同一个镜像、只是换了个容器格式，就又踩了一次** ——
  而且这次是**照抄自己写的另一个文件**踩的。
- **解决**：在 `CostField.raw()` 里把两种约定都写成注释贴着代码，
  并**在跑之前用「直线代价剖面」做自检** —— 剖面里 `cost=0` 的段必须和地图上
  实际空旷的位置对得上，对不上就说明换算错了。
- **教训**：
  1. **PGM 和 OccupancyGrid 的行方向相反**，这是两个独立的约定，代码里必须写死注释。
  2. **自检优先于排查**：这次的症状是「数字自相矛盾」（路径撞障碍、长度荒谬），
     而不是「结果不太好」。**遇到自相矛盾，先怀疑自己的坐标换算，再怀疑被测系统。**
  3. 我在这个 bug 上先怀疑了「代价地图时刻不一致」，写了诊断代码 —— **顺序反了**。
     正确第一步是：拿一个**已知点**回代，看格号对不对
     （F-1 的「解决」里就写了这一条，我没执行）。

### F-18 测量函数中途 `return`，把「部分量」当成「总量」

- **问题**：`tools/probe_planner.py` 报「规划路径长度 **0.64 m**」，而请求的起终点相距 6.68 m。
- **现象**：同一行还打出「路径经过障碍 (1.66,1.43)」和「代价积分 **inf**」——
  三个数字**互相矛盾**（长度荒谬、路径撞障碍、代价无穷）。
- **原因**：采样函数写成了「一撞到障碍就 `return`」，于是返回的「长度」其实是
  **从起点到第一个障碍的距离**，不是整条路的长度。
  ⚠️ 这条和 F-17（坐标镜偿）是**两个独立的 bug 叠在一起** ——
  修掉 F-17 后本条依然存在。
- **解决**：采样函数**不在中途返回**，改成把「障碍穿越点」收集起来一起返回；
  长度累加与「是否撞障碍」解耦。

  ```python
  total += seg / n                       # 长度总是累加
  if nc is None:
      integ += 254.0 * (seg / n)         # 撞障碍计一个高分，但不停
      hits.append((x, y))
  ```

- **教训**：「部分量」和「总量」**同形同单位**，肉眼分不出来。
  所以函数返回值要么带一个「是否完整」的标志，要么就不允许中途退出。
  **自检办法**：拿一个**已知答案**的输入对 —— 例如直接用起点→终点的直线
  （长度可手算：`hypot(Δx, Δy)`），对不上就是量错了。

### F-19 在控制/发布循环里做耗时的事，把频率压到 `cmd_vel_timeout` 以下

- **问题**：用监视脚本驱动机器人时，机器人**一顿一顿**，让它走 3 m 只走了 0.125 m。
- **现象**：`diff_drive_controller` 的 `cmd_vel_timeout: 0.5 s`（即要 ≥2 Hz）。
  脚本把 `/cmd_vel` 的发布写在采样循环里，而循环每次都要 `subprocess` 调一次
  `gz model`（约 300 ms）→ 实际发布频率掉到约 **1.8 Hz < 2 Hz**。
- **原因**：**控制频率被「测量」污染了**。一旦超过 `cmd_vel_timeout`，控制器就把速度归零，
  于是机器人走走停停。看起来像「驱动器有 bug」或者「参数配得太保守」。
- **解决**：**发布用独立的定时器**，控制循环里只更新「目标速度」这个变量：

  ```python
  node.create_timer(0.05, self._publish)   # 20 Hz，与自己算得多慢无关
  def _publish(self): ... self.pub.publish(self.tv, self.tw)
  ```

  计算/规划/测量再慢也不会影响发布。
  （`tools/map_coverage.py`、`tools/probe_costmap.py`、`tools/probe_dwb.py` 都按这个写法。）
- **教训**：**测量者和被测量者要在时间上解耦。**
  同一个循环里又「做重活」又「发心跳」，一定会互相打架。

### F-20 把「事件驱动」的话题当成周期性数据源

- **问题**：用订阅 `/amcl_pose` 的方式采 AMCL 位姿，脚本一直卡在等第一条消息。
- **现象**：脚本跑了几十秒没任何输出，看起来像挂了；但手动 `ros2 topic echo /amcl_pose` 又能看到数据。
- **原因**：`/amcl_pose` **不是周期性发布的**。AMCL 只在位姿变化超过
  `update_min_d: 0.25 m` / `update_min_a: 0.2 rad` 时才发一条 ——
  **车不动就一条都不发。**
- **解决**：卡在「等第一条」的地方加超时 + 说明；要评估**静止**时的定位，
  改用 `tf2_echo map base_footprint`（TF 是周期性广播的），或直接查 `map→odom` 变换。
- **教训**：**「没数据」和「没在发」是两回事。**
  接一个话题前先确认它是**周期性**还是**事件驱动**的 ——
  用 `ros2 topic hz` 看，或读那个节点里 `update_min_*` 这类阈值参数。
  本仓库里同类话题还有：`/initialpose`（只在设定时发）、
  `/evaluation`（只在控制器跟踪路径时发）、`/costmap_updates`（只在有变化时发）。

## G. 脚本与 Docker 的组织

### G-1 `compose.yaml` 必须和 wrapper 同层（不能收进 `docker/`）

- **问题**：根目录平铺了 22 个文件，想把 `compose.yaml` / `Dockerfile` /
  `entrypoint.sh` 收进 `docker/`，让根目录只剩目录和 README。
- **现象**：评估时发现这不是「改几个路径」的事——所有 wrapper 都是
  `cd "$(dirname "${BASH_SOURCE[0]}")"` 之后就地处跑**裸 `docker compose`**（不传 `-f`），
  compose 文件一旦不在同一层，全部报 `no configuration file provided: not found`。
- **原因**：`docker compose` 默认只读**当前工作目录**的 `compose.yaml` /
  `compose.override.yaml`。更麻烦的是 compose 里三处路径都是**相对 compose 文件所在目录**
  解析的：`build.context: .`、`volumes.source: ..`（挂给 `/workspace`）、
  `${GZ_CACHE_DIR:-./gz-cache}`。移动 compose 文件会把这三处**一起悄悄指错**
  （`/workspace` 会变成挂 `my-slam` 自己），而不会报任何错。
- **解决**：不动 compose 那一组。只把 16 个脚本收进 `scripts/`，
  `compose.yaml` / `compose.nvidia.yaml` / `Dockerfile` / `entrypoint.sh` / `ros-env.sh`
  留在仓库根，`container-exec.sh` 改成 `cd` 到自己的**上一级**。
  事前已核对 `name: slam-ros2-dev` 与 `container_name: slam-ros2-dev` 都是显式写死的，
  所以项目名和容器名不受文件位置影响。

### G-2 靠 `$BASH_SOURCE` 定位目录的脚本，一移动就静默指错一级

- **问题**：脚本从仓库根挪进 `scripts/` 后，路径解析全错。
- **现象**：`docker compose` 找不到配置文件；`check-models.py` 跑完输出一堆模型问题，
  看起来正常，其实它扫的是 `scripts/gz-cache/models`（不存在），没报错只是因为
  「扫到 0 个模型」和「全部通过」在输出上很像。
- **原因**：`"$(dirname "${BASH_SOURCE[0]}")"` 解析的是**脚本自己所在目录**，
  文件一移动这个值就变了；而拿到一个不存在的路径通常不抛异常，只是返回空结果。
  ⚠️ 最容易漏的是**只做 `exec` 转发的脚本**：`docker_run.sh` → `start.sh`、
  `docker_stop.sh` → `stop.sh`，它们要的恰恰是「脚本自身目录」，
  **不能**跟着改成上一级（否则会去找 `my-slam/start.sh`，那个文件不存在）。
- **解决**：按用途分成两类逐个处理——需要 compose 的（`container-exec.sh`、
  `start.sh`、`stop.sh`、`gpu-check.sh`）改成 `.../..` 并加注释；
  只转发兄弟脚本的（`docker_run.sh`、`docker_stop.sh`）保持原样。
  改完逐个 **实跑** 验证（`bash -n` 语法检查一律通过，但语法检查抓不到这类错）。

### G-3 「依赖只装在容器里」要先分清是镜像的问题还是容器的问题

- **问题**：`docker diff` 显示 `tf_transformations`、`example_interfaces` 在容器里是
  `A`（相对镜像新增），第一反应是「`Dockerfile` 漏了这两个包」，差点去改 Dockerfile。
- **现象**：`my_tf_pkg/package.xml` 确实依赖 `tf_transformations`，
  `learn_executor_cpp` 的 `CMakeLists.txt` 确实依赖 `example_interfaces` ——
  看起来是个真实的隐患。
- **原因**：只查了**运行中的容器**就去推断 `Dockerfile`。实际上 `Dockerfile` 第 86-88 行
  早就有这两个包（提交 `b696fe9` 加入），而且**当前镜像里也确实有**
  （直接 `docker run --rm --entrypoint bash slam-ros2-dev:jazzy -c 'ls -d ...'` 验证过）。
  真实情况是**容器比镜像旧**：容器创建于 `2026-10-01 09:58 +08:00`，
  镜像构建于 `2026-10-01 12:56 +08:00`，是后来重新 build 过镜像但没重建容器。
- **解决**：结论是**无实际故障**（容器能用、镜像也正确，只是容器旧）。
  判定方法固定为两条命令：
  `docker inspect <容器> --format '{{.Created}}'` 对比
  `docker image inspect <镜像> --format '{{.Created}}'`；要查镜像里到底有什么，
  直接起一个一次性容器看，不要拿运行中的容器当镜像的证据。
  这条与 A-3 是同一个问题，A-3 的修法（补进 Dockerfile 并重建镜像）是对的。
