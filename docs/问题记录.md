# 问题记录

本文件记录本项目（`my-slam`，Ubuntu 24.04 aarch64 / ROS 2 Jazzy / Gazebo Harmonic）
在建设过程中**实际遇到并已解决**的问题，统一按四段式记录：

> **范围**：把整套示例代码移植到本工作空间、并适配到 Jazzy 的全过程。
> 涉及的包包括：机器人描述与 Gazebo 仿真、Nav2 导航参数、自定义规划器/控制器插件、
> 各类应用节点与学习型示例包、bringup 启动，以及自研的传感器桥接。
> 本文件按**问题类型**归类，不按来源划分。

| 字段 | 含义 |
| --- | --- |
| **问题** | 一句话概括是什么事 |
| **现象** | 具体看到的报错、日志或表现（尽量贴原文） |
| **原因** | 查证后的真实根因（**没查证的不写**，只写"未定位"） |
| **解决** | 实际采用的改法；若有代价或副作用也写出来 |

书写约定：
- 只记录**有证据**的结论。凡是推测，明确标注「推测」或写「原因未定位」。
- 报错原文用代码块或行内代码给出，方便直接搜。
- 与架构相关的取舍写在「解决」里的"代价"中。

## A. 构建与环境

### A-1 容器里装不了系统包

- **问题**：想在容器里 `apt install`，一直失败。
- **现象**：`apt` 报权限错误；容器默认登录用户是 `nvidia`，不是 root。
- **原因**：`compose.yaml` 里以非 root 用户运行（这是有意的，避免产物属主变成 root）。
- **解决**：走 docker 显式指定用户，不用 `sudo`：

  ```bash
  docker compose -f my-slam/compose.yaml exec -T -u root slam-ros2-dev \
    bash -lc 'apt-get update && apt-get install -y <pkg>'
  ```

  **代价**：`-u root` 装出来的文件属主可能是 root，装完注意别让构建产物被 root 污染。

### A-2 `packages.ros.org` 慢到不可用

- **问题**：`apt-get update` 拉 ROS 索引要两分多钟。
- **现象**：实测 `packages.ros.org` 约 **14 KB/s**（2.0 MB 索引 ≈ 140 s）；
  换成 `mirrors.ustc.edu.cn` 约 **5.8 MB/s**，快约 400 倍。Ubuntu ports 官方源同样慢。
- **原因**：境外源在本机网络环境下带宽受限。
- **解决**：`Dockerfile` 新增的依赖层默认走国内镜像（`APT_USE_CN_MIRROR=1`），
  需要时可用 `--build-arg APT_USE_CN_MIRROR=0` 切回官方源。
  **注意**：镜像里 apt 源是"永久改写"的（用 `while` 循环写的，不是 `trap`），
  重建后容器内的源会一直指向 USTC/TUNA。

### A-3 依赖只装在运行中的容器里，重建就没了

- **问题**：`ros-jazzy-tf-transformations`、`ros-jazzy-example-interfaces` 装好了能跑，
  但换台机器 / 重建容器就报找不到。
- **现象**：编译时报 `Could not find ... example_interfaces`。
- **原因**：依赖只装进了**当时正在运行的那个容器实例**，没有写进 `Dockerfile`
  （镜像构建时间早于 `Dockerfile` 改动时间）。
- **解决**：把两个依赖补进 `Dockerfile` 的依赖层，**重建镜像**，并进容器验证已固化。

### A-4 `--symlink-install` 下新增文件也必须重新编译

- **问题**：改了代码却"没生效"，或者"明明文件在源码里，install 里却没有"。
- **现象**：新写的 `bringup_sim.launch.py` 在 `install/` 里找不到。
- **原因**：`colcon build --symlink-install` 是**逐文件建软链**。改已有文件不用重编
  （软链自动指向新内容），但**新增文件没有对应的软链**，必须重编才会生成。
- **解决**：新增文件后一定重新 `colcon build --symlink-install`。

### A-5 宿主机没有 numpy，跑不了仓库里的分析脚本

- **问题**：在宿主机上跑不了仓库里的分析脚本。
- **现象**：`python3 tools/check_map_point.py` 报
  `ModuleNotFoundError: No module named 'numpy'`。
- **原因**：脚本是给容器内用的，宿主机 Python 没装 numpy。
- **解决**：所有分析脚本都在容器里跑：

  ```bash
  docker compose -f my-slam/compose.yaml exec -T slam-ros2-dev \
    bash -lc 'cd /workspace/my-slam && python3 tools/xxx.py ...'
  ```

## B. Nav2 参数：Humble → Jazzy 迁移

> 这一批是沿用 Humble 时代写法的配置，直接拿到 Jazzy 下用必然撞到的坑。全部改动集中在
> `src/navigation/mybot_navigation2/config/nav2_params.yaml`，每条都在注释里留了原始报错。

### B-1 插件类名分隔符变了

- **问题**：`planner_server` / `controller_server` 起不来，说插件类不存在。
- **现象**：`planner_server: class ... does not exist`（控制器侧同）。
- **原因**：插件类名的写法从 `包名/类名` 改成了 `包名::类名`（C++ 作用域解析）。
- **解决**：全部写成 `nav2_navfn_planner::NavfnPlanner`、`dwb_core::DWBLocalPlanner` 这种形式。

### B-2 手写 `plugin_lib_names` 会导致重复注册并崩溃

- **问题**：bt_navigator 一启动就报重复注册，容器直接段错误。
- **现象**：

  ```text
  ID [ComputePathToPose] already registered
  ```

  随后 `component_container_isolated` 段错误。
- **原因**：配置里在 `plugin_lib_names` 下**逐个列出了全部内置 BT 节点**；Jazzy 已经自动
  注册了这些节点，再列一遍就是重复注册。
- **解决**：把 `bt_navigator.plugin_lib_names` **整段注释掉**（Jazzy 会自动注册）。
  **坑里有坑**：不能改成 `plugin_lib_names: []`（空列表）——会报
  `Expected 'value' to be one of [float, int, str, bool, bytes], but got '()' of type 'tuple'`
  导致 launch 直接失败。**只能注释掉**。

### B-3 Jazzy 会无条件启动 `collision_monitor`，缺配置就报错

- **问题**：启动 Nav2 时 `collision_monitor` 报参数未初始化。
- **现象**：`parameter 'observation_sources' is not initialized`。
- **原因**：原来的 `nav2_params.yaml` 里根本没有 `collision_monitor` 段，
  但 Jazzy 的 launch 会把它拉起来。
- **解决**：在参数文件里补一段 `collision_monitor` 配置（用雷达做 `observation_sources`）。

### B-4 Jazzy 会无条件启动 `docking_server`，缺配置报两个错

- **问题**：`docking_server` 起不来，报类型不兼容 + 没给插件。
- **现象**：

  ```text
  incompatible type ... Twist_
  Charging dock plugins not given!
  ```

- **原因**：同样是没有配置段，而 Jazzy 会启动它；且它需要
  `enable_stamped_cmd_vel` 与 `dock_plugins`。
- **解决**：补 `docking_server` 配置段，含 `enable_stamped_cmd_vel: True` 与
  `dock_plugins: ['simple_charging_dock']`。

### B-5 `Twist` → `TwistStamped`：车收到指令却不动

- **问题**：Nav2 一切正常、规划也出来了，**车就是不动**；手动发 `/cmd_vel` 能动。
- **现象**：Nav2 日志里看不到明显错误；`/cmd_vel` 上没数据或类型不匹配。
- **原因**：Jazzy 的 Nav2 节点默认发 `geometry_msgs/msg/TwistStamped`，
  而差速控制器按配置订阅带时间戳的版本；类型/开关不一致，指令就断在中间。
- **解决**：在**5 个**节点里都加 `enable_stamped_cmd_vel: True`：
  `controller_server`、`behavior_server`、`velocity_smoother`、`collision_monitor`、
  `docking_server`。
  **验证方法**：`ros2 topic info /cmd_vel --verbose` 看类型是否为 `TwistStamped`。

  > 顺带记录速度链拓扑（本项目实测，改参数前必须知道）：
  > `controller_server` / `behavior_server` → `/cmd_vel_nav` → `velocity_smoother`
  > → `/cmd_vel_smoothed` → `collision_monitor` → `/cmd_vel` → 差速控制器。
  > `docking_server` 只在对接时也直接发 `/cmd_vel`。

### B-6 参数名单复数写错

- **问题**：`progress_checker` 配置不生效。
- **现象**：按单数名去查是 `Parameter not set`，按复数名 `progress_checker_plugins`
  才能取到 `['progress_checker']`。
- **原因**：Jazzy 里是复数 `progress_checker_plugins`，原来的写法是单数。
- **解决**：改成 `progress_checker_plugins: ['progress_checker']`。

### B-7 轮距 `wheel_separation` 与 URDF 不一致

- **问题**：车走直线跑偏、原地转向角度不准，进而影响建图与定位质量。
- **现象**：`mybot_ros2_controller.yaml` 里 `wheel_separation: 0.17`，
  而 URDF 里两轮安装位置是 `y = ±0.10`（即 0.20）。
- **原因**：这个 0.17 是更早版本的数值，没有跟着 URDF 一起更新 ——
  轮距曾经按 URDF 修正过一次，但那份修正没有同步到本文件，于是又用回了旧值。
- **解决**：按 URDF 证据固定为 `wheel_separation: 0.20`，并做 A/B 实验验证：

  | 配置 | 真值终点与目标的偏差 |
  | --- | --- |
  | 0.17 | **−14.96%** |
  | 0.20 | **−0.41%** |

  复核脚本：`tools/verify_wheel_separation.py`。

### B-8 运行时 `ros2 param set` 改轮距"看起来生效了其实没有"

- **问题**：用 `ros2 param set` 把 `wheel_separation` 改成 0.20，跑完发现"改了没差别"，
  差点得出"该参数无影响"的错误结论。
- **现象**：`ros2 param set` 返回 success，但车的运动学行为完全没变。
- **原因**：`diff_drive_controller` **不会在运行时重新读取该参数**，必须重启控制器。
- **解决**：
  1. 要改轮距 → 改配置文件后**重启控制器**；
  2. 加一个独立手段确认"参数真的作用到了被测对象上"
     （`tools/probe_wheel_speed.py` 由轮速反推实际下发的参数值）。
  **教训**：先证明"测量本身有效"，再下结论。

## C. 插件与节点代码

自定义规划器 `nav2_custom_planner`、自定义控制器 `nav2_custom_controller`
两个包从能编译、能加载到能跑通，一共 **4 类**问题（C-1 ~ C-4）；
其余节点/包代码在移植时的问题见 **C-5 起**。

### C-1 `nav2_core/exceptions.hpp` 这个头文件没了

- **问题**：插件包编译不过。
- **现象**：`fatal error: nav2_core/exceptions.hpp: No such file or directory`
- **原因**：Jazzy 把这个头拆成了四个专用头。
- **解决**：按角色选用 —— 规划器用 `nav2_core/planner_exceptions.hpp`，
  控制器用 `nav2_core/controller_exceptions.hpp`（另有 `smoother_exceptions.hpp`
  / `route_exceptions.hpp`）。

### C-2 抽象类实例化失败：`createPlan` 签名变了

- **问题**：插件包编译不过。
- **现象**：`invalid new-expression of abstract class type 'CustomPlanner'`
  （提示 `createPlan` 未覆盖纯虚函数）
- **原因**：Jazzy 的 `GlobalPlanner::createPlan` 多了一个参数
  `std::function<bool()> cancel_checker`。
- **解决**：补上该参数，并在生成路径的循环里用它实现"中途可取消"。

### C-3 抛出的异常类型不对，导致异常永远不会被捕获（隐藏 bug）

- **问题**：控制器插件里抛异常后行为异常，但没有对应的错误日志。
- **现象**：日志里看不到预期异常处理路径。
- **原因**：代码抛的是 `nav2_core::PlannerException`，而 `controller_server`
  只捕 `nav2_core::ControllerException`。
  用 `strings libcontroller_server_core.so` 验证过，里面只有
  `N9nav2_core19ControllerExceptionE`。
- **解决**：控制器插件里改成抛 `nav2_core::ControllerException`。
  **这条是"编译能过、逻辑能跑，但错误处理静默失效"的典型隐藏 bug，值得单独记。**

### C-4 插件描述文件 `.xml` 缺 `name` 或用了旧分隔符

- **问题**：插件编译通过，但运行时加载不到类。
- **现象**：启动时报找不到插件类。
- **原因**：
  - `nav2_custom_controller.xml` **整段缺少 `name` 属性**；
  - `nav2_custom_planner_plugin.xml` 里写的是 `nav2_custom_planner/CustomPlanner`
    （旧分隔符）。
- **解决**：补上 / 改为 `name="nav2_custom_planner::CustomPlanner"`、
  `name="nav2_custom_controller::CustomController"`。

> **刻意选择**：插件包虽然编译、加载、跑通（到位误差 0.077 m），但
> `nav2_params.yaml` 里**默认仍用官方 `DWBLocalPlanner` / `NavfnPlanner`**，
> 自定义插件作为注释掉的备选。理由是默认路径更稳，自定义插件主要用于演示。

### C-5 发导航目标时朝向是非法四元数

- **问题**：C++ 节点发目标点后，消息里的 `orientation` 是非法姿态。
- **现象**：只填了 `position`，`orientation` 保持默认全 `0`（即 `w=0, x=y=z=0`），
  不是合法的单位四元数。
- **原因**：构造目标消息时漏填 `orientation`。
- **解决**：补上 `goal_msg.pose.pose.orientation.w = 1.0;`（显式表示"朝向不变"）。
  **注意**：这个改动对可观测结果**没有影响**（改前改后 Nav2 行为一致），
  目的是消除非法四元数、不给下游留隐患。不要把它当成"修好了某个 bug"来宣传。

### C-6 包里的节点没全部注册，`ros2 run` 找不到

- **问题**：包里 4 个节点只有一个能跑起来。
- **现象**：`ros2 run <包名> <节点名>` 对除一个之外的节点都报找不到可执行文件。
- **原因**：`setup.py` 的 `console_scripts` 里**只注册了一个入口点**。
- **解决**：把该包的 4 个节点全部注册进 `console_scripts`。

### C-7 语音播报节点的依赖不存在，一启动就崩

- **问题**：语音播报节点启动就 `ImportError`。
- **现象**：模块顶层直接 `import espeakng`，而本机没有 `espeak-ng`、也没有音频设备。
- **原因**：硬依赖一个本机不存在的包。
- **解决**：改成 `try: import espeakng`，失败时**降级为只打日志**；
  **服务名、服务类型、返回值全部保持不变**，所以调用方完全无感。
  **代价**：本机不会真的发声 —— 这是环境限制，不是遗漏。

### C-8 仿真出的相机话题名和代码里写的不一致

- **问题**：抓拍功能拿不到图像。
- **现象**：代码订阅 `/camera/image`，但仿真里发布的是 `/camera_sensor/image_raw`，
  话题对不上，回调永远不触发。
- **原因**：两侧话题名不一致。
- **解决**：在 launch 里做 remap `/camera_sensor/image_raw` → `/camera/image`，
  同时注入 `use_sim_time`，并把 `image_save_path` 指到工作区目录（先 `mkdir -p`）。
  **只动 launch，不动节点的 `.py`**，保证节点代码与原实现一致、方便对照。

### C-9 真机启动文件在本机跑不起来（已知限制，按原样保留）

- **问题**：真机用的 bringup 启动文件在本机直接报错退出。
- **现象**：

  ```text
  PackageNotFoundError: "package 'ydlidar' not found"
  ```

- **原因**：它依赖 `ydlidar`、`micro_ros_agent`、`ros_serial2wifi` 三个包，
  而本项目目前只做仿真，没有（也不需要）安装它们。
- **解决**：**按原样保留，不在本地强跑**。
  但顺手修掉了这个文件里一个**真实的拼写错误**：`ros_serail2wifi` → `ros_serial2wifi`
  —— 拼错的话即使装了包也找不到。这个错误与仿真无关，是真 bug，值得单独记。

### C-10 编译时的弃用告警

- **问题**：编译过程出现弃用告警。
- **现象**：`rmw_qos_profile_services_default` 被标记为已弃用。
- **原因**：Jazzy 改成了直接构造 QoS 对象。
- **解决**：改用 `rclcpp::ServicesQoS()`。

## D. 传感器桥接

### D-1 部分话题桥接失败（`/imu`、`/camera/*`）

- **问题**：`parameter_bridge` 建不出 `/imu` 和 4 个 `/camera/*` 的桥，
  这 5 个话题在 ROS 侧根本不存在。

- **现象**：

  启动日志里每一条失败的桥都报同一句：

  ```text
  [WARN] [ros_gz_bridge]: Failed to create a bridge for topic [/imu] with ROS2 type
    [sensor_msgs/msg.Imu] to topic [/imu] with Gazebo Transport type [gz.msgs.IMU]:
    No template specialization for the pair
  ```

  **受影响**：`/imu`、`/camera/image`、`/camera/depth_image`、`/camera/camera_info`、
  `/camera/points`（一批里通常有 4~5 条建不出来）。
  **不受影响**：`/clock`、`/scan`、`/scan/points`、`/odom`、`/tf`、`/joint_states`。

  这个现象**很误导人**：`gz topic -i -t /imu` 能看到 gz 侧确实有发布者、数据也在出，
  但 `ros2 topic list` 里根本没有 `/imu` —— 看着像“话题丢了”，其实是桥没建起来。

  2026-09-30 当时记录下来的观察（都在这个环境里实测过）：

  | 观察 | 结果 |
  | --- | --- |
  | 同一份参数连跑 3 次 | 失败集合**完全相同**，不像“时好时坏” |
  | 单独桥 `/imu`（`@` 双向 / `[` 单向都试） | **建得出来、零告警** |
  | 两个参数的组合 | 正常 |
  | 把话题名换成 `/a` `/b` `/c` | 结果一样 —— 与话题名无关 |
  | `/scan` + `/scan/points` + `/imu` 三条一组 | imu 必失败，换顺序也一样 |
  | 换参数**顺序**（`clock,clock,scan,spts,imu` vs `scan,spts,clock,clock,imu`） | 失败集合会变 |
  | 同一会话开头能全通，之后却稳定失败 | 会漂移 |
  | 重启容器后立刻重测 `/imu` | 仍失败 —— 不是“容器跑久了才坏” |

  另外：**gdb 会影响结果**（gdb 默认关 ASLR），说明结果对内存布局/时序敏感。

- **原因**：⚠️ **未定位。**

  2026-09-30 当时的结论是「上游 arm64 构建缺陷」—— **该结论已于 2026-10-01 撤回**。
  当时做过的排除（都排掉了，所以只能停在“未定位”，而不是“就是上游”）：

  | 排查项 | 做法 | 结果 |
  | --- | --- | --- |
  | 不是本仓库配置问题 | 参数、话题名、方向符、顺序都验过 | 排除 |
  | 不是文件损坏 | `dpkg -V` | 无输出（文件与包元数据一致） |
  | 不是版本旧 | 与清华镜像比对 | 已是 apt 源里最新的 arm64 版本 |
  | 不是依赖装漏 | `ldd` | 无 `not found` |
  | 不是共享内存耗尽 | `/dev/shm` 用量 | 64 MB 里只用了 4% |
  | 不是残留进程干扰 | 清理干净后重测 | 同样复现 |

  **2026-10-01 复核：复现不出来。** 在同一个容器里（未重建镜像、未换容器）用
  `tools/probe-bridge-types.sh` 逐个场景重试，那个失败**一次都没再出现**：
  单条 `/imu`（单向/双向）、当时记录在案的「失败组合」、原始的 9 条桥 +
  `--ros-args` remapping（当年失败的完整配置）、7 条桥一次性传入 —— 全部 **0 失败**。
  尤其「仿真运行中单独桥 `/imu` 必失败」这条被**直接证伪**。

  所以：当时的观察应该是真的，但**原因至今未定位、且当前无法复现**。
  当初把它归因于上游缺陷属于**推测**，不成立 —— 那段“最硬的证据”（gdb 打断点看到
  key 正确）依赖按 aarch64 ABI 从 `x0/x1` 取参，而 Release 构建没有调试信息，
  这种取参方式本身有误读风险，不能拿来证明“库内部查表返回了 null”。

- **解决**：

  **当时的处理**：改用本仓库自研的 `gz_sensor_bridge` 节点 —— 直接用 gz-transport
  订阅 gz 话题，按上游 `ros_gz_bridge/src/convert/sensor_msgs.cpp` 的转换逻辑构造
  ROS 消息再发布，保证下游（rviz / slam_toolbox / nav2）看到的东西和官方桥一致。
  ⚠️ 它当时的定位是「绕开上游 bug 的必要手段」，**这个理由已不成立**。

  **现在的处理：两套实现都保留，用 launch 参数二选一**（实测两者等价）：

  ```bash
  ./sim.sh --clean --headless -- sensor_bridge:=parameter_bridge   # 内置桥
  ./sim.sh --clean --headless                                     # 默认：自研桥
  ```

  两者只影响 `/imu` 与 `/camera/*`；`/scan`、`/scan/points`、`/clock` 一律交给
  `parameter_bridge`。**绝不能同时开** —— 同一话题会出现两个发布者。

  | 项目 | `parameter_bridge` | `gz_sensor_bridge`（默认） |
  | --- | --- | --- |
  | 6 个传感器话题的发布者数 | 全 = 1 | 全 = 1 |
  | `/scan` | 9.94 Hz | 9.97 Hz |
  | `/imu` | 99.43 Hz | 99.60 Hz |
  | `/camera/camera_info` | 9.94 Hz | 9.99 Hz |
  | `/imu` 的 `frame_id` | `imu_link` | `imu_link` |
  | 数据自洽自检 | 退出码 0 | 退出码 0 |
  | 启动日志里 ROS→GZ 桥 | 0 条 | 0 条 |

  保留自研桥的理由是：已验证可用、有测试覆盖，删掉没有收益。

  **若日后再现**：先跑 `bash tools/probe-bridge-types.sh` 把输出存下来 ——
  那份材料才有资格报上游。切换实现后请跑 `tools/check_topic_health.sh` 确认
  发布者数仍为 1。

### D-2 双向桥造成自激回环，`/scan` 频率飙到 18000 Hz

- **问题**：激光话题频率暴涨到完全不可用，还白烧 CPU。
- **现象**：`/scan` 从 5 Hz 飙到 **~18000 Hz**。
- **原因**：gz 的激光**本来就发布在 `/scan` 上**；如果桥再建一条 ROS→GZ 方向，
  桥会订阅自己的输出并写回 gz `/scan`，形成自激回环：
  `激光 → 桥 → ROS /scan → 桥自己订阅 → 写回 gz /scan → 桥再收 → …`。
- **解决**：`/scan`、`/scan/points` 只建**单向** `[`。
  **检查方法**：启动日志里 `grep -c "Creating ROS->GZ Bridge"` 应该是 **0**；
  `ros2 topic info /scan -v` 的 Publisher count 应该是 **1**。

### D-3 残留进程导致同一话题多个发布者，频率翻倍

- **问题**：某个话题的频率是期望值的 2~3 倍，数据重复。
- **现象**：`/imu` 曾测出 **300 Hz**（期望 100 Hz）。
- **原因**：清理脚本的进程名列表里**没包含新增的常驻节点**，
  所以 `--clean` 没把旧实例清掉；ROS 侧同一个话题于是出现多个发布者。
- **解决**：**往 launch 里新增常驻节点时，必须同步把它的进程名加进清理列表**。
  **检查方法**：`ros2 topic info /imu -v | grep "Publisher count"` 应该是 **1**。

## E. 行为异常排查（不是配置错）

> 这一类最容易误判成"配置写错了"。**先排除外部因素，再怀疑参数。**

### E-1 Nav2 反复 `Failed to make progress`，恢复次数耗尽后 ABORT

- **问题**：发目标 `(-4.5, 1.5)` 时，Nav2 反复报错并最终放弃，车停在中途不动。
- **现象**：

  ```text
  [controller_server]: Failed to make progress
  [controller_server]: [follow_path] [ActionServer] Aborting handle.
  ```

  `number_of_recoveries` 一路涨到 13~15，最后 `error_code: 105` 且
  `Goal finished with status: ABORTED`；车停在 `(-8.88, -0.55)`。

- **原因**：**不是配置 bug，是「临界 + CPU 争抢」导致的概率性失败。**
  同一份起点/目标，实测**既出现过 5 次恢复就成功（`error_code: 0`、距目标 0.23 m）**，
  **也出现过 15 次恢复后 ABORT**。

  逐项排除如下（每条都有实测证据）：

  | 怀疑对象 | 怎么验的 | 结论 |
  | --- | --- | --- |
  | 车物理被卡住 | 在它停下的位置手动发 `0.25 m/s` → 车走了 **1.16 m**；激光正前方 2.02 m 无障碍 | ❌ 排除 |
  | AMCL 定位飘了 | `/amcl_pose` 与 `gz model -p` 真值逐点对比，全程偏差 **1~3 cm** | ❌ 排除 |
  | `collision_monitor` 压速度 | 它全程只打了启动横幅，之后再无任何消息 | ❌ 排除 |
  | 速度链上某级吃掉指令 | 同时录 `/cmd_vel_nav`、`/cmd_vel_smoothed`、`/cmd_vel`，三级**完全一致**（都 47% 非零、范围都是 `[0, 0.26]`） | ❌ 排除 |
  | 目标几何上不可达 | `tools/map_reachability.py`：最宽路线最窄处半径 **0.750 m** ≫ 车半径 0.22 m | ❌ 排除 |
  | 仿真太慢导致 10 秒窗口不够 | RTF ≈ **1.00**；`use_sim_time` 全为 `True`；progress checker 两参数未设 = 默认 10 s / 0.5 m | ❌ 排除 |

  **`Failed to make progress` 本身报得没错**，它是症状不是原因 ——
  把报错时刻和真实位置对齐，10 秒位移实测 0.16 / 0.05 / 0.00 / 0.01 m。

  唯一站得住的相关因素：**同期的 Nav2 自己报了控制环性能不足**：

  ```text
  [controller_server]: Control loop missed its desired rate of 20.0000 Hz.
                       Current loop rate is 5.7471 Hz.
  [planner_server]:    Planner loop missed its desired rate of 20.0000 Hz.
                       Current loop rate is 1.3605 Hz.
  ```

  控制环只有配置值（20 Hz）的 1/3~1/4，DWB 的轨迹采样与打分质量必然下降。

- **解决**：
  - 跑 Nav2 相关验证时**不要同时开 rviz / Gazebo GUI**，先把 CPU 让出来；
  - 复现/观察：`bash tools/run-stuck-repro.sh`
    （瞬移回起点 + 按真值对齐 AMCL + 同时录整条速度链，一遍看完）；
  - **不要**为了这个去改 Nav2 参数 —— 参数本身没问题，是资源不够。

### E-2 「只打日志说明」的噪声：`Failed to transform initial pose in time`

- **问题**：设 AMCL 初始位姿时几乎必打这行警告，看着像失败了。
- **现象**：

  ```text
  [amcl]: Failed to transform initial pose in time (Lookup would require
    extrapolation into the future.  Requested time 1923.414000 but the latest
    data is at time 1923.405000, when looking up transform from frame
    [base_footprint] to frame [odom])
  ```

- **原因**：`odom→base_footprint` 这条 TF 比仿真时钟滞后约 0.2~0.3 s
  （`/odom` 是 50 Hz，但 TF 时间戳落后于 `/clock`）。
- **解决**：**不用管**。实测三种时间戳策略后 `/amcl_pose` 与真值的偏差分别是
  0.016 m / 0.053 m / 0.036 m，位姿都确实生效了；而且设定前 AMCL 一直在打
  `AMCL cannot publish a pose or update the transform. Please set the initial pose...`
  （= 没有位姿），设定后立刻正常发布 `map→odom`。
  **不要为了消这行日志去调时间戳，那是白费功夫。**

### E-3 设初始位姿用了墙上时间，AMCL 不认

- **问题**：发了 `/initialpose` 但 AMCL 不更新位姿。
- **现象**：`/amcl_pose` 不出新值、`map→odom` 不发布，AMCL 持续打
  `AMCL cannot publish a pose or update the transform. Please set the initial pose...`。
- **原因**：仿真里 AMCL 用**仿真时间**（`use_sim_time: True`），
  而初始位姿消息带的是墙上时间戳，对不上。
- **解决**：`use_sim_time=True`，且时间戳置 **0**（让 tf2 取最新可用变换）。
  已固化在 `tools/set_initial_pose.py` 里，支持 `--from-gz` 直接对齐真值。

### E-4 「绕远路」不是 bug

- **问题**：目标直线距离 6.68 m，Nav2 却报 `distance_remaining` 18.17 m。
- **现象**：规划出来的路径明显绕远，接近直线的 3 倍。
- **原因**：navfn 默认 `use_astar: false`，是**按代价最小**而不是距离最短找路；
  膨胀层（`inflation_radius`）会给墙附近一大片格子加代价，如果直线全程贴着墙，
  它的累计代价可能高于一条更长但更空旷的路。
- **解决**：确认车确实能走直路之后，可选：
  - 调小 `inflation_radius`（0.55 → 0.3 左右）或 `cost_scaling_factor`；
  - 或把 `planner_server` 里 `use_astar` 改成 `true`。
  排查手法：`python3 tools/map_clearance.py --from 2.17 1.88 --to -4.5 1.5`。

### E-5 里程计漂移（`open_loop: true`）

- **问题**：巡逻一圈后 `/odom` 与真值差很多，看起来像定位坏了。
- **现象**：实测一圈后 `/odom` 报 `(3.58, 6.16) yaw ≈ −168°`，
  而真值是 `(4.57, −1.17) yaw ≈ 154°`，差了 7 m / 38°。
- **原因**：`mybot_ros2_controller.yaml` 里 `open_loop: true`，
  里程计**按"指令速度"积分，不看轮子实际转了多少**；仿真里原地转向时轮子会打滑，
  这部分打滑里程计完全看不到。
- **解决**：**不是 bug，真机也一样** —— 这正是必须要 AMCL / 建图的原因。
  AMCL 会把它纠正回来，所以导航到位误差仍只有 0.2 m 级。
  想直观感受：对比 `tf2_echo map base_footprint`（已纠正）和
  `ros2 topic echo /odom`（未纠正）。

### E-6 rviz2 显示的内容和这个项目无关

- **问题**：打开 rviz2 后看不到本项目的东西。
- **现象**：界面里出现的显示项和订阅话题都是 TurtleBot3 的，本项目的话题一个都看不到。
- **原因**：默认配置是给 TurtleBot3 用的。
- **解决**：用 `tools/gen_nav2_rviz.py` 生成裁剪过的配置。

### E-7 rviz2 一次性启动崩溃（环境问题，非配置）

- **问题**：`rviz2` 启动就崩。
- **现象**：进程启动后立即因 SIGSEGV 退出，窗口起不来。
- **原因**：环境相关（EGL 软件渲染）。
- **解决**：**已证明与配置无关**（换配置后两种都能稳定跑 50 s）。
  这类问题不要往配置上查。

### E-8 相机帧率只有 3~4 Hz

- **问题**：`/camera/image`、`/camera/depth_image` 频率明显低于配置值。
- **现象**：`/camera/camera_info` 稳定跑在配置的 **10 Hz**，
  而 `/camera/image`、`/camera/depth_image` 只有 **3~4 Hz**。
- **原因**：瓶颈是 **Gazebo 的离屏渲染**，不是桥 ——
  否则 `camera_info`（不需要渲染）也会一起掉。
- **解决**：**不用解决**。这两个话题的数据本身是正确的，只是刷新慢。

## F. 自己写分析脚本时踩的坑（方法论）

> 这一节记录的是**我（开发/分析方）自己的错误**，不是项目代码的错。
> 之所以单列，是因为这两条都差点导致"基于错误测量得出重大结论"。

### F-1 从 PGM 行号反推 y 时方向写反，整张图在 y 上被镜像

- **问题**：手写脚本扫描 `room.pgm` 时，把障碍的 y 坐标说错了。
- **现象**：报出“障碍在 y≈0.9”，实际位置在 y≈−5.2，差了约 6 m；
  并据此写了一整段错误推理。
- **原因**：**PGM 的首行对应 y 最大值**，正确换算是
  `row = h - 1 - int((y - oy) / res)`。但是遍历时按这个公式取行、
  却用 `y0 + i * res` 去标注行号，标签和真实 y 就差了一个镜像。
- **解决**：
  - **不要手写扫描脚本**，用已验证的工具：
    `tools/map_reachability.py`、`tools/map_clearance.py`
    （这两个的行列换算都验证过）；
  - 真要自己写，先拿一个**已知点回代**验证。

### F-2 占用判据和 `map_server` 不一致，凭空造出一大片墙

- **问题**：把 `room.pgm` 的中间灰度当成障碍，得出了假的“目标不可达”结论。
- **现象**：按错误判据会在地图上多出一大片不存在的墙；同一目标另一次运行又能到达，
  说明结论不自洽。
- **原因**：`room.yaml` 是 `mode: trinary`，`occupied_thresh=0.65`、
  `free_thresh=0.25`，`map_server` 按 `occ = (255 − pixel) / 255` 判断：

  | pixel | occ | 判定 | 本图占比 |
  | --- | --- | --- | --- |
  | 0 | 1.000 | **障碍** | 3463 px |
  | 205 | 0.196 | **自由** | 3157 px |
  | 254 | 0.004 | **自由** | 76852 px |

  **205 是自由空间，不是"未知区域"**。把它当障碍，地图上就会多出一大片
  不存在的墙。

- **解决**：判禁用 `pixel <= 100`（等价于 `occ > 0.65`），
  或直接用 `tools/map_reachability.py`（判据写在文件开头的说明里）。
  **自检技巧**：故意放一个"预期不可达"的输入做对照实验
  —— 例如 `(4.5, 1.5)` 那格是 `cafe_table_1`，脚本正确报"不可达"，说明方法可靠。

### F-3 `set -u` 会让 `source ROS 的 setup.bash` 静默把脚本打掉

- **问题**：分析脚本跑起来没有任何反应。
- **现象**：脚本“没有任何输出、退出码 1”，看着像逻辑错误。
- **原因**：ROS 的 `setup.bash` 会引用未定义变量，在 `set -u` 下会直接终止当前 shell；
  而脚本里又写了 `source ... >/dev/null 2>&1`，把报错一起吞了，于是表现为"什么都没发生"。
- **解决**：不要在 `source setup.bash` 之前开 `set -u`（或干脆不用）。
  本仓库的脚本按此约定：**先用 `source`，再考虑其它 shell 选项**。

### F-4 `ros2 topic echo` 走管道时输出会被整体缓存

- **问题**：用 `ros2 topic echo` 叠加管道做时序记录时，时间戳全部失效。
- **现象**：所有记录的时间戳**都一模一样**（都等于最后一条的时间）。
- **原因**：管道里 `ros2 topic echo` 的输出被整体缓冲，下游（awk / while read）
  只在进程结束时才一次性收到全部数据。
- **解决**：需要"带时间戳的时序记录"时，**用 rclpy 写订阅者**自己打时间戳
  （见 `tools/probe_cmd_chain.py`、`tools/probe-localization-vs-truth.sh`），
  不要指望 `echo | 管道`。

### F-5 嵌套引号把 heredoc 搞坏

- **问题**：多层嵌套的命令行怎么都跑不起来。
- **现象**：`docker ... bash -lc '... python3 - <<"PY" ... PY'` 报
  `zsh: no matches found: ...`，命令整段没执行。
- **原因**：内层 Python 代码里含有**单引号**（例如
  `'障碍' if x else '自由'`），把外层的单引号提前闭合了。
- **解决**：这种多层的命令不要硬凑，**写成脚本文件**再调用
  （本仓库 `tools/` 下的一堆脚本就是这么来的，同时也方便复用和 review）。

### F-6 长驻命令不要接 `head`

- **问题**：用 `head` 截断长驻命令，会得到“话题挂了”的假结论。
- **现象**：`timeout 12 ros2 topic hz /scan | head -1` 输出
  `topic [/scan] does not appear to be published yet`，看起来像话题挂了。
- **原因**：管道提前关闭导致上游命令报假错误。实际上 `/scan` 好好的
  （`ros2 topic info /scan` 显示 Publisher count: 1，实测 9.99 Hz）。
- **解决**：不要用 `head` 截断长驻命令；用 `ros2 topic echo --once` 验证。

### F-7 `pkill -f` 会杀掉自己

- **问题**：清理进程的脚本会把自己也杀掉。
- **现象**：脚本执行后立即结束，看不到任何输出。
- **原因**：`pkill -f 'navigation2.launch.p[y]'` 里的模式能匹配到**同一条命令行
  后半段**的字面量，于是 pkill 把自己的 shell 也杀了。（踩过两次。）
- **解决**：把 pkill 模式**放进脚本文件**（`tools/stop-nav2-patrol.sh`、
  `tools/stop-sim.sh`），杀进程那条命令行里只出现脚本路径，不可能自匹配。

### F-8 `ros2 action list` 读的是 daemon 缓存

- **问题**：想用它判断 Nav2 是否还活着，结果不准。
- **现象**：节点已经退出（或还没起来），它仍然能把 action 列出来。
- **原因**：它读的是 ROS daemon 的发现缓存，不是实时状态。
- **解决**：不能用来判断节点存活。要看进程用 `pgrep`，
  要看话题通不通用 `ros2 topic info --verbose`。

### F-9 把「无法复现的故障」归因成「上游缺陷」

- **问题**：一轮排查没定位到原因，就把结论写成「上游 arm64 构建缺陷」，
  并据此写了文档、定了架构（改用自研桥绕开）。
- **现象**：这个结论写进了 README、launch 注释和自研桥源码头部，并被当成
  “已确认”引用；过了一天（换了个时间点、什么都没改）**全部复现不出来**。
- **原因**：犯了两个错 ——
  1. 把**观测**当成了**解释**。「同一份参数连跑 3 次失败集合相同」是观测；
     「所以是上游库的缺陷」是解释，中间那一步没有证据。
  2. 用了一个**本身不可靠的取证手段**（Release 构建下按 ABI 从寄存器取函数参数），
     就把它当成“最硬的证据”。
- **解决**：
  - 严格区分「观察到什么」和「为什么」，后者没证据就写**未定位**；
  - 排除法只能得出“**不是**这些原因”，**不能**推出“就是那个原因”；
  - 下结论前先问一句：**换个时间点还能复现吗？** 复现不了的故障不要写成结论。
  - 已撤回的 3 处：README 对应小节、launch 注释、`gz_sensor_bridge_node.cpp` 文件头。

### F-10 `git mv A dir/` 在 `dir` 不存在时是「重命名」，不是「移入」

- **问题**：把 22 个包分到 4 个子目录时，4 个包被**改了名**，还把其他包嵌套进了包内部。
- **现象**：`src/robot` 里装的直接是 `mybot_description` 的内容（`urdf/`、`world/`…），
  而 `mybot_bringup`、`gz_sensor_bridge` 被塞进了这个包目录里；
  `src/navigation` = 旧 `mybot_navigation2`、`src/app` = 旧 `mybot_application`、
  `src/learning` = 旧 `learn_compose`。
- **原因**：`git mv 源 目标目录/` 只有**目标目录已存在**时才移入；不存在时按「重命名」处理，
  **不会自动建目录**。第一次执行 `git mv src/mybot_description src/robot/` 真的是把包
  改名成了 `robot`，之后几条才变成“移入”。
- **解决**：目标写成**完整路径**（`git mv src/pkg src/group/pkg`），或先 `mkdir -p src/group`。
  已经错了的话，用显式路径修：先把被吐进来的包挪到暂存目录，把组目录名改回包名，再逐个放进组里。

### F-11 zsh 不对未加引号的变量做单词切分

- **问题**：用 `for p in $PKG_LIST` 批量移动包，循环只跑了一次且报 `bad source`。
- **现象**：`git mv "src/learning/$p" ...` 报
  `fatal: bad source, source=src/learning/learn_dds_cpp learn_executor_cpp ...`
  —— 整串被当成了**一个**路径。
- **原因**：**zsh 默认不做 word splitting**（bash 会）。`$PKG_LIST` 展开后仍是单个词，
  `$(find ...)` 的输出同理。
- **解决**：改为逐条写显式路径（本次采用）、或用 zsh 数组 `pkgs=(a b c)`、
  或显式开启切分 `${=PKG_LIST}`。写「批量操作一批路径」的脚本时优先用**数组**。
